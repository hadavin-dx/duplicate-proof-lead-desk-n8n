# Why this code exists

The question for every part: is there a ready-made tool that already does it? The rule followed: try the ready-made
tool first, use the Python standard library second, write own code last, and only for what a tool does not give.
The order of tools tried: (1) a workflow tool with no code (n8n), (2) the standard library, (3) a free library or
program, (4) own code. This table says where each part ended up and what only the own code gives. "Not checked" means
that tools were not compared for that part in this repository; there is no claim that no tool exists. Terms (atomic insert, UNIQUE key, test doubles, Host and Origin check, CRM dump, UNKNOWN) are explained in the README under "Words used here" and in `docs/tests.md`.

Only n8n was compared for the main question (the first row); no other tool was evaluated for any row marked "Not checked".

| Part | What it has to do | Tried first | What only own code gives | Result |
|---|---|---|---|---|
| Decide "new lead or duplicate" and remember it | One decision per email address, even when ten requests arrive at once, and a way back after a crash | n8n alone, four patterns, tried once on one computer (the workflows and logs are not in this repository, see the README). Only n8n was tried: no idempotency or outbox library, queue or other tool was compared | No n8n-only result is stated here (tried once by the author, logs not shipped, see the README); the desk writes each step down first and either finishes it or marks it UNKNOWN for a person, so a crash between the CRM step and the email step is covered by tests in this repository | Own code (`src/lead_desk/desk.py`, `gate.py`, `db.py`); this is the part the demo is about (the other parts of the desk are listed in the rows below) |

## Where another service plugs in

The desk talks to three things through three interfaces in `src/lead_desk/contract.py`: `Crm` (the customer database), `Outbox` (the mail sender) and `Qualifier` (the AI step). Each has a stand-in in `demo_only/` and the kinds that can be selected are closed lists in `src/lead_desk/constants.py`: `CRM_CHOICES` (`fake`, `hubspot`), `OUTBOX_CHOICES` (`http`, `smtp`, `smtp_provider`) and `QUALIFIER_CHOICES` (`recorded`, `live_claude`). `src/lead_desk/loader.py` turns the chosen kind into an object. To use another CRM, mail service or AI service, do all of these (a test fails if one is missed): (1) write a module that implements the interface (see `src/lead_desk/crm_hubspot.py` and `src/lead_desk/smtp_provider.py` as examples); (2) add its name to the tuple in `constants.py` (and, for a mail kind that stays on this computer, to `OUTBOX_STAND_INS`); (3) add one branch for it in `loader.py`; (4) make sure `Config.real_services` in `config.py` counts it as a real service, so the banner, the demo-tools gate and the loopback-only bind rule apply; (5) for a CRM kind, add its entry to `CRM_FIELDS_SENT` in `portal_api.py`, which says which lead fields it is sent and drives the data page; (6) the interface adapters that talk to the stand-ins live in `src/lead_desk/adapters.py` and the stand-ins themselves in `demo_only/`; a real kind goes in its own module under `src/lead_desk/` and must not import from `demo_only/`. This demo ships exactly one real CRM kind (HubSpot) and one real AI kind (`live_claude`, which calls one vendor's API); mail has the vendor-neutral `smtp_provider` kind. The tests run these kinds against stand-ins (the only real-service try is described in `docs/hubspot-probe.md`); no second CRM or AI service is built here.
