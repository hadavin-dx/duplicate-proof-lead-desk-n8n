# Real-services check

**You do not need this section to run the demo.** The steps above use only the demo stand-ins.
This section is for someone who wants to try the desk against their own free HubSpot account and their own mailboxes.
This script is an untested reference: it was exercised only against the demo stand-ins (`--dry-fakes`), so what follows describes a script, not a result.

This script has not been run against a real HubSpot account or a real Gmail mailbox. The only real-service try so far is the separate, small script `scripts/hubspot_probe.py` (`docs/hubspot-probe.md`): tried by the author on a free HubSpot account, logs not shipped. Everything else in this repository ran against demo stand-ins. The script described here is the way to try the rest; until a run is recorded in this file, treat the real-service behaviour as untested, including what the code assumes about HubSpot (for example that it refuses a second create of the same email with a message naming the existing contact).

`scripts/run_real_check.py` runs the same desk against a real CRM (a free HubSpot account) and real e-mail (a mail account reached over an encrypted connection), then COUNTS what really happened. Only the INPUT is made up: about 12 invented people at the address ending `example.com` (the reserved example domain; a real CRM may refuse `.test` addresses); nobody outside your own inboxes receives anything. You run it from your own terminal; it asks "y/N" after printing the worst-case number of calls, mails and dollars, and it refuses to start without explicit caps.

1. Copy `scripts/real-run.env.example` to a folder outside the repository and fill it in. Each name is explained inside the file. Secrets are never in that file, only the paths of one-line key files (a CRM service key with contacts read and write only; a mail app password).
1a. **Before turning lead stages on in any real HubSpot account (required):** the CRM admin lists every automation that reacts to lead status changes and confirms each one is safe or switched off; test on one made-up contact first. The desk writes the lead status field and cannot see those automations (`docs/limits.md`, section "Which CRM stage things the desk touches").
2. In HubSpot create the contact property `hadavin_lead_id` (single-line text) by hand; the program never creates properties.
3. Self-test first, no real service: `python scripts/run_real_check.py --dry-fakes`. Then the real run: `python scripts/run_real_check.py --config PATH`. Options: `--live-model` (a real AI model, its own dollar cap in the `DESK_LIVE_*` names), `--cleanup` (archives only the contacts this run made, found by their lead ids).

It sends new people, repeats through the same door and the other door, one person with two different addresses (a CRM that only compares email addresses sees two different people, so it cannot catch that; the desk also treats them as two leads, and the result says so), stops the desk hard once after the load started, restarts it, and re-sends. It then reads back the CRM contacts by `hadavin_lead_id`, counts the mails in your two receiving mailboxes at different providers (for example one Gmail and one Google Workspace mailbox; one block per mailbox in the config) by the header `X-Send-Key` (no body or address is read) and prints only counts and a pass/fail table of the checks, plus a per-lead table. The same goes into a JSON file.

What it would show: the number of CRM contacts per lead id, the desk's own count of calls and creates, and the number of mails that reached your mailboxes per lead, after a crash and with repeats through both doors. What it would NOT show: that mail would reach a stranger's inbox (no spam-folder, SPF or DKIM claim: it counts what arrived in your two mailboxes and their spam folders; one message per lead is allowed across both mailboxes together), that the CRM's own e-mail de-duplication did not hide something (the evidence would be the desk's own counts plus the different-address case), or anything about volumes beyond the free plan's limits. After a hard crash a mail that was in flight is recorded `unknown` on purpose: the table shows how many of those arrived.

Exit code 0 only when every check in its table passes: the book holds all the leads, the follow-ups that were not in flight at the crash ended `sent`, the mailboxes hold a mail for every `sent` follow-up, the CRM holds a contact for every lead marked done, and the first desk process really stopped at the crash point. Failure tables print no address and no setting value. The CRM key is sent only to the CRM vendor's own API host names (any other host needs a setting that says so). The full list of checks is in the script's own help text; its exit codes and settings names are in `docs/settings.md`.

**Where the files may be.** The config file, and the folders that the config names (`DESK_DB_PATH` and so the run folder, `REAL_RESULT_FILE`, the key and password files), can be anywhere on the computer, also outside the repository: the script reads the config you name with `--config` and uses the paths in it as written. The folder checks of `load_tools/README.md` (`LEAD_DESK_PATH_ROOTS`) do not apply to them, because they come from your own files and not from a command line that a faulty script might have filled in. Only the config path itself is checked (no control characters, links are followed, the file must exist), and it is found by looking the name up in the folder listings from the top of the disk (or the network share), so it must be a file in a folder you can list: a config below a folder that you can enter but not list, or one handed over as `--config <(command)`, is refused with a message (copy it to a normal file).
