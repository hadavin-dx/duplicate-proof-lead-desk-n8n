# Crash points, promises and tests

This page holds the detail behind the short summary in the README.

## How to run the tests

The tests need development tools, installed from a lock file into the `.venv` folder so that nothing else on your computer changes.

Windows PowerShell (Python 3.13 matches the lock file), with the `.venv` folder switched on as in the README, "Try it":

    python -m pip install --require-hashes -r requirements-dev-win.txt
    python -m pytest -q                                  # the tests

Linux (Python 3.12 matches the lock file), with the `.venv` folder switched on as in the README, "Try it":

    python -m pip install --require-hashes -r requirements-dev.txt
    python -m pytest -q                                  # the tests

The SonarQube job (`.github/workflows/sonar.yml`) also measures how much of the code the tests run. On Linux, instead of the install line above, install the dev lock and the coverage lock (it adds `pytest-cov` and `coverage`) in one pip call, as the job does; pip stops with an error if a package is pinned to two different versions in the two files. Then add the coverage options:

    python -m pip install --require-hashes --only-binary=:all: -r requirements-dev.txt -r requirements-coverage.txt
    python -m pytest -q --cov --cov-report=xml:coverage.xml

The settings are in `pyproject.toml` (`[tool.coverage.run]`); the report `coverage.xml` is read by the SonarQube scan through `sonar.python.coverage.reportPaths`. The browser tests skip without Playwright, so the figure counts code that only they reach as not run.

The desk alone: `PYTHONPATH=src python -m lead_desk.server`. The crash scene: `PYTHONPATH=src python scripts/crash_desk.py`, then write a point name (for example `D2`) into the flag file it prints, and the next time the desk reaches that point it ends at once. On Windows set `PYTHONPATH` with `;` between entries when two are needed (`src;.`). The tests set the path for their own processes. Writing `blind` instead of `keyed` in the start command starts a mail system that cannot recognise repeats.

The desk's settings (the `DESK_*` names, plus the extra names of the real-services script and `N8N_URL`, `N8N_API_KEY_FILE` and the `DPLD_*` names; n8n's own `N8N_PORT` and similar are in `docs/n8n-recipe.md`) are in `docs/settings.md`; the exit codes of the desk are in `docs/limits.md`.

The automatic checks in `.github/workflows/lint.yml` are: ruff (style), mypy (types), bandit (known insecure patterns), a schema check, gitleaks (secrets and other leaked values, on the files and the history), a scan for hardcoded addresses, links, absolute paths, e-mail addresses and long tokens, and the whole test suite. A second workflow, `.github/workflows/codeql.yml`, runs GitHub's CodeQL scan (Python, the portal's JavaScript and the workflow files themselves). A fourth, `.github/workflows/semgrep.yml`, runs the open-source Semgrep scanner (see "Semgrep" below); the third, `sonar.yml`, is described with the review services below. `.github/dependabot.yml` asks for version updates of the GitHub Actions. A test (`test_workflows_are_pinned_and_limited`) fails if a workflow uses an Action that is not pinned by its full commit SHA, has no read-only top-level `permissions:` block, or uses a trigger that passes secrets to pull-request code. Two review services read the pull requests once their owner has switched them on in their own settings: CodeRabbit (configured by `.coderabbit.yaml`) and SonarQube Cloud (a scan run by `.github/workflows/sonar.yml`, configured by `sonar-project.properties`; it uses the repository secret `SONAR_TOKEN`, and SonarQube Cloud's automatic analysis must stay off for this project). These files only configure the services; whether a service is switched on, and what it found, is not stated in this repository. No result of any of these is claimed here. `tools/hygiene.py` also has an optional scan for a list of terms that the person running it supplies; it does nothing without that list. `.env` files are never used: the demo needs no secrets.

## Semgrep

`.github/workflows/semgrep.yml` runs the open-source Semgrep scanner (its own pinned, hash-checked install in `requirements-semgrep.txt`; no account, no token, no usage data sent) on every pull request and every push to main. It reads the rule packs `p/python` and `p/javascript` from the public Semgrep registry over `src`, `scripts`, `load_tools`, `tools` and `n8n`, and fails the job on a finding of severity ERROR. After the install the job runs `pip check` and `semgrep --version`, so that a package missing from the lock file is reported as an install problem and not as a finding. The findings are printed in the job log only (no code-scanning upload). It belongs with the checks of `lint.yml` and the tests, and it needs the five folders above (a missing folder makes Semgrep exit 2, which the job retries three times and then fails with a message naming the possible causes). **Network use of the job:** pip downloads the packages of the lock file from the Python Package Index file hosts (every file is checked against its hash); `actions/setup-python` may download a CPython 3.12 build (GitHub-hosted releases of Python builds) when the runner does not already have it; Semgrep downloads the two rule packs from the Semgrep rule download service (a host name that ends in `.dev`) at every run; checkout reads this repository from GitHub. No other host is contacted by the job's own commands, and `--metrics=off` and `--disable-version-check` stop Semgrep's usage report and version check. Tests in `tests/test_nosemgrep_form.py` run the real scan step against a stand-in `semgrep` (only exit 2 is retried) and compare the parsed workflow with an exact whitelist: the triggers, the permissions, the concurrency block, one job on `ubuntu-24.04` with a time limit of at most 20 minutes, exactly five steps with exactly the expected keys (no `if`, `shell`, `working-directory`, `continue-on-error`, extra `env` or extra action), the two Actions pinned to the same commit ids as `lint.yml`, the install command word for word, and the scan command word for word (so a new flag, a `--config=...` or `--exclude=...` form, another pack or a missing folder fails). They also refuse an expression such as `github.event.`, `github.head_ref` or `github.ref_name` inside a `run:` step and any secret or token reference. These tests do not prove the workflow is safe or that it scans correctly on GitHub; they pin its shape and the retry logic (against a stand-in `semgrep`).

**Status of the scan:** the first live run of this workflow on GitHub, as read from the job log by the project lead (not by the author of this note): run 43403502735, 2026-11-13, head 15b8b15e. The log says "Scanning 64 files tracked by git with 79 Code rules" and "Ran 77 rules on 47 files: 0 findings", and the job ended with exit code 0 (Semgrep 1.185.0, `p/python` and `p/javascript`, severity ERROR, `--strict`, the five folders above). Why the numbers differ (79 rules and 64 files in the first line, 77 rules and 47 files in the second) is not explained here. **A green job alone does not prove that rules ran:** a job can end green with no rules loaded or no files read. The proof is the log line "Ran N rules on M files": after any change to the packs or the folders, read it and check that N and M are not zero and are plausible. This workflow has no check of its own for those numbers. `tests/` and `demo_only/` are not scanned, and findings of lower severity were not looked at. The rules are fetched live, so a later run can give other numbers. An earlier run by the lead, on commit 0841f36 of a branch that is not in main's history (in the `semgrep/semgrep:1.185.0` container image, without `--strict`, with `--quiet`), also had no ERROR finding; the live run above replaces it as the status. If a run fails on a finding that already exists, fix the code or suppress that one finding as described below in a separate change.

**Licence and the public log:** the rules are under the Semgrep Rules License v1.0 (own internal use only, no redistribution; see the legal page on the Semgrep website; the licence text was not fetched or read for this check, so the terms named here are not checked against it). The repository owner has said yes to this use of the registry packs `p/python` and `p/javascript` for this repository only; no other pack is covered. The job log of a public repository prints the rule ids and rule messages of every finding, so anyone can read them; the files in this repository contain no copy of any rule.

**What is scanned, and what is not:** `tests/` is left out on purpose: it holds planted fake secrets, hostile inputs and deliberately insecure code that exist to be caught by other checks, and Semgrep would report them. `demo_only/` (fake services and a demo page) is left out because it is not code the desk runs for real. This is a decision made without a scan result; add either folder to the command in the workflow and in the line below if you want them read. `n8n` holds 3 JSON files (the workflows) and is only nominal: no rule pack runs on JSON, and JavaScript inside an n8n Code node is not parsed, so Semgrep does not review the n8n workflows. A comment cannot be put in JSON either, so there is nothing to suppress there.

**Exit codes of the scan** (seen with the pinned Semgrep 1.185.0): 0 = no finding; 1 = at least one finding (the job prints "findings above" and fails; findings are never retried); 2 = the registry could not be reached or a scan path does not exist (the job retries up to three times, 20 seconds apart, then fails); 7 = a rule file or address that cannot be read; any other non-zero code is a tool error (the job prints that it is not a finding). 3 = some files that cannot be parsed, when `--strict` is on (as the job has it). Measured with Semgrep 1.185.0, a made-up rule and no network: a Python or a JavaScript file with an unclosed call bracket (`print("hit"` or `eval("hit"`, alone or after a broken `def` or `function` line) made Semgrep exit 3 with `--strict` and exit 0 without it, and the job would then fail with the message "not findings" (it is not retried). The share of lines read does not predict this: it was about 0 to 100 percent in those files. Not every syntax error does it: `def f(:` followed by `  pass`, and `function f( {` followed by `}`, were read in full (about 100 percent) and gave exit 0 even with `--strict`. When another file has a real finding, the exit code is 1. So some files that Semgrep cannot read make the job fail: this is how `--strict` behaves, not a finding. A run of the same kind on the five folders above (a made-up rule for Python and JavaScript, not the registry packs, 47 files on 61ded9e plus this change) gave exit 0 with and without `--strict` and about 100 percent of lines read; that can change when the files change. The rules are fetched live and cannot be pinned, so the registry can change what this check reports without any change here: keep it out of the required checks, and if the job fails with exit 2 after three tries, re-run it later.

**Run it on your own computer** from the repository root, in a Python 3.12 virtual environment, with network access (the rules are downloaded): on Linux x86_64 `pip install --require-hashes --only-binary=:all: --no-deps -r requirements-semgrep.txt`, anywhere else `pip install semgrep==1.185.0` (the version pinned in `requirements-semgrep.in`), then `semgrep scan --metrics=off --strict --error --severity ERROR --config p/python --config p/javascript src scripts load_tools tools n8n`. The job adds `--disable-version-check` (no check for a newer Semgrep); on your computer you may leave it out.

**To suppress one wrong finding:** write `# nosemgrep: <rule-id> <reason>` in Python, or `// nosemgrep: <rule-id> <reason>` or `/* nosemgrep: <rule-id> */` in JavaScript, on the line of the finding or on the line above it (for a finding that spans several lines, the first line), with the rule id the log printed, for example `# nosemgrep: python.lang.security.audit.dangerous-subprocess-use.dangerous-subprocess-use the command is a fixed list`. The short spelling `nosem` works the same way in Semgrep and follows the same rule. A suppression without a dotted rule id is refused by a test (`tests/test_nosemgrep_form.py`): Semgrep reads a bare `nosemgrep` or `nosem`, and a colon with nothing after it, as "hide every finding on this line" (checked with the pinned version on a made-up rule); it also reads `nosem` followed by any letters, in any upper or lower case, and with the long s `ſ` (U+017F) in place of the `s`, as a suppression, so the test refuses those spellings too. A tab after the colon is read like a space (the id after it is used), so `nosemgrep:` TAB id is accepted by the test like the space form. The `--ignore-gitleaks-allow` switch of the lint job concerns gitleaks only and has nothing to do with this. The repository owner approves any suppression in the pull request.

**To bump the Semgrep version:** follow the comment at the top of `requirements-semgrep.in`. Dependabot is set up for GitHub Actions only, so it covers none of the lock files, this one included; the repository owner checks for a newer version when a Semgrep security advisory appears or about once a quarter. The lock files of this repository were made by two tools: `pip-compile` made `requirements-dev.txt`, and `uv` made the other lock files (`requirements-dev-win.txt`, `requirements-coverage.txt`, the two browser locks and `requirements-semgrep.txt`); the uv version is written down only for the coverage lock (0.11.32, in `requirements-coverage.in`) and the Semgrep lock (0.13.8, in `requirements-semgrep.in`), and each header or comment gives the exact command. The Semgrep lock and the dev lock are separate installs in separate jobs, so a shared package (for example `typing-extensions`) may have a different version in each; that is harmless.

## Browser tests

Some tests drive the portal in a real web browser. For that they need Playwright (a Python package that remote-controls a browser) and a copy of the Chromium browser. Without them these tests are skipped, not failed. They are in `tests/test_portal_browser.py`, `tests/test_portal_lead_pages.py`, `tests/test_stage_confirm_browser.py`, three in `tests/test_portal_wording_and_masking.py`, a few in `tests/test_mode_safety.py`, and the layout and look tests (`tests/test_portal_layout.py`, `tests/test_portal_look.py`), which use the same browser helpers. **The checks in `.github/workflows/lint.yml` install only `requirements-dev.txt` and there is no browser job yet, so they do not run the browser tests;** the masking promise P10 rests on them, so run them on your own computer.

Playwright is not in the development lock files. It has its own optional lock file, `requirements-browser.txt` (Linux x86_64, Python 3.12) or `requirements-browser-win.txt` (Windows, Python 3.13), with hashes. It holds Playwright 1.63.0 and the three packages Playwright needs (greenlet, pyee and typing-extensions; typing-extensions has the same version as in the development lock). Nothing else is needed: the two sidebar tests read the colours of a screenshot inside the browser itself, so no image library such as Pillow is required. Install it after the development lock, in the same `.venv`:

    python -m pip install --require-hashes -r requirements-dev.txt
    python -m pip install --require-hashes -r requirements-browser.txt      # on Windows: requirements-browser-win.txt
    playwright install chromium

Two settings you may need before the tests run, only if the browser or Node is not in its default place (Node is a program that runs JavaScript; some tests run the portal's script with it). Linux (bash):

    export PLAYWRIGHT_BROWSERS_PATH=<folder that holds the browser>
    export PATH=<folder that holds node>:$PATH

Windows (PowerShell):

    $env:PLAYWRIGHT_BROWSERS_PATH = "<folder that holds the browser>"
    $env:Path = "<folder that holds node>;" + $env:Path

Then run the tests (the `-rs` option prints one line for each reason a test was skipped):

    python -m pytest -q -rs

Measured on Linux with Python 3.12, one run, 2026-11-12: a new `.venv` with both lock files installed with `--require-hashes`, Chromium build 1243 and Node 22 (v22.23.4) already present in folders of their own (written as placeholders above), so `playwright install chromium` itself was not run there. That step on a computer without a browser was not measured, and Windows was not measured (the Windows lock file was made but never installed).

Playwright 1.63.0, the version in the lock, looks for build 1243, which is what `playwright install chromium` fetches for it. A newer Playwright wants a newer build: the Playwright 1.65.1 package names build 1254 (both build numbers were read from the `playwright/driver/package/browsers.json` file inside each package on 2026-11-12). If only build 1243 is installed, a newer Playwright does not find its build and every browser test is skipped with a "BrowserType.launch: Executable doesn't exist" message. Keep the Playwright version in the lock and the installed build together.
* **Where the browser is not in the default place,** set `PLAYWRIGHT_BROWSERS_PATH` to the folder that holds it: the tests start the browser with no path of their own.

## Quality checks and what to do when a check fails

The commands for ruff, mypy, bandit and the schema check are listed under "Quality commands" in `contract.md`, and the same commands, in order, are in `.github/workflows/lint.yml` (that file also has the secret scan and the scan for hardcoded literals). Run them from the repository folder with the `.venv` folder switched on.

When a check fails: read the last lines of its output first; they name the file and line. For a test, run it alone (`python -m pytest -q tests/test_name.py::test_name`). A test that did not run is not a pass: to see why tests were skipped, run `python -m pytest -q -rs`, which prints one line per skip reason (for example "could not import 'playwright.sync_api'", "node is not installed", "no gitleaks program on PATH"). To make a missing secret scan a failure instead of a skip, set `DPLD_REQUIRE_SCAN=1` and `GITLEAKS_BIN` to the program's path.

What the two secret checks reported, measured on 2026-11-13 with gitleaks 8.30.1 and this repository's `.gitleaks.toml`. The test values were made up and put after the prefix `hadavin-dx_` in lines that start with `sonar.projectKey=` or `x_api_key=`, in files named `cfg.txt`, `notes.properties` and `x_api_key.txt`. Gitleaks (rule `generic-api-key`) reported values of 20, 30, 40, 50 and 60 random lowercase letters and digits. It did not report values of letters only, of words joined by hyphens, or of one repeated letter, at any of those lengths. One digit added to the hyphenated words made gitleaks report them; one digit added to the repeated letter did not. So the cause looks like "no digit" or "too little variety" in the value, not the prefix; the rule inside gitleaks was not read. The real project key holds a digit and was reported once its allowlist was removed. A prefix inside a line of ordinary text was not reported by gitleaks at any length.

The repository scan (`patterns.txt`, pattern 9, `[A-Za-z0-9+/=_-]{40,}`) reports an unbroken run of 40 or more of those characters. The prefix and a key name before `=` count towards the 40; a dot, a space or a quote ends the run. It reported every `key=value` line above, so a letters-only second project key in `sonar-project.properties` is seen by that scan alone. The exception for the real key (last line of `exceptions.txt`, the `sonar.projectKey` allowlist in `.gitleaks.toml`) therefore has to stay exact. `tests/test_gitleaks_exceptions.py` plants near-misses in a temporary copy and fails if either exception is widened. To add a second key of this shape, add its exact text, never a wider pattern or a whole file, and keep that test passing. `.gitattributes` forces LF endings; the real line with CRLF endings is reported by gitleaks, not by the repository scan. If `sonar-project.properties` or `exceptions.txt` was saved with CRLF (or a lone carriage return), `tests/test_hygiene.py` says so and names two cures, and a test runs both on a planted file, once before and once after `git add`. Cure 1, `git checkout -- <file>`, throws away your edits and works only if you have not run `git add` or `git commit` on the file: measured with git 2.43 in a real clone with `core.autocrlf=true` (a planted tree gave the same with `false`), after `git add` or a commit each of `git checkout -- <file>`, `git checkout -f -- <file>`, `git restore <file>`, `git update-index --really-refresh` and `git add --renormalize <file>` left all 14 carriage returns in a CRLF file, and `git restore --worktree --source=HEAD <file>` and `git checkout HEAD -- <file>` did too for CRLF and for a committed lone CR (git sees the file as unchanged), but those last two do cure a lone CR that was only staged, while `git status` and `git diff` before the cure did not stop it from working. Cure 2, the Python one-liner in the message, keeps your edits and works in every state (write `python3` on macOS or Linux, `py -3` on Windows if `python` is not found; replace `<file>` with the path); if you had run `git add` or `git commit`, run it again after the cure. Deleting the file and running cure 1 is not offered: after `git add` it removes a CRLF but brings a lone carriage return back from the index (measured). `sed -i 's/\r$//'` is not offered: it is GNU-only and leaves a lone carriage return. The cures were not run on real Windows. Why only those two files, measured on 2026-11-13 with gitleaks 8.30.1 by turning one file at a time into CRLF in a clean checkout: `sonar-project.properties` makes `gitleaks dir` report the key line (`test_hygiene_scan_public` fails); `exceptions.txt` makes the `grep -v -E -f exceptions.txt` step of `lint.yml` keep every line (that CI step would fail; the tests read the file with Python and still pass); `.gitleaks.toml`, `patterns.txt` (`git grep -f` found the same lines) and the `requirements-*.txt` and `.in` files made no difference (`pip` was not run on the lock files).

## What each promise rests on

The desk was stopped on purpose at each of ten crash points and restarted; nine of them are simulated by an exception raised inside the program, and only D2 is a real process kill (`docs/limits.md`). The table says what had happened at each point and what the result was. "Keyed" and "blind" are explained in the README under "Words used here". The two columns are the kind of MAIL system. The outcome at C0 and C1 depends on the kind of CRM instead (both mail kinds gave the same result in the tests, `tests/test_flow.py`, `EXPECT_MORE`), so those two rows say so in words.

| Point | What had happened | Keyed mail system | Blind mail system |
|---|---|---|---|
| A | the receipt is written, no verdict yet | one email | one email |
| A2 | the verdict and the lead are written inside the open transaction but not yet committed (a real kill here loses them; the receipt stays open and the restart decides it) | one email | one email |
| B | the verdict is recorded | one email | one email |
| L | the AI label is stored | one email | one email |
| C0 | the desk has noted that it is about to write to the CRM, but has not written yet | with a keyed CRM (either mail system): the CRM is asked and holds one row, one email. With a blind CRM (either mail system): it is not asked again after a crash (a put may have started), so the CRM holds no row, no email is sent, and the follow-up is UNKNOWN (the reason is `crm_unconfirmed`) until a person looks | (same: this row depends on the CRM kind, not the mail kind) |
| C1 | the CRM write came back but the desk has not yet noted it | with a keyed CRM (either mail system): asked again with the same key, one email. With a blind CRM (either mail system): never asked twice, so one CRM row, no email, and the follow-up is UNKNOWN until a person looks in the CRM | (same: this row depends on the CRM kind, not the mail kind) |
| D1 | at the start of the send step, before the send is marked | one email | one email |
| D1b | the send is marked but the mail system has not been called | one email | no email, UNKNOWN |
| D2 | the email was sent but the result is not yet noted | one email | one email, follow-up UNKNOWN (the desk cannot tell whether it left, so it does not resend) |

"Mutation check": the code is deliberately broken in one known way (on the test side only) and the named test must fail with the named symptom. `test_mutant_no_unique_key` removes the database rule that two leads cannot share an email and the lookup; the duplicate test must fail with "leads == 1" and "got 2". `test_mutant_no_claim` removes the check that only one retry may take a follow-up; the retry test must fail with "emails == 1" and "got 2". This shows the tests notice these two faults; it is not proof that the code is correct.

## Terms for developers

* **Atomic insert**: a database write that either happens completely or not at all.
* **UNIQUE key**: a database rule that refuses a second row with the same value (here, a second lead with the same email address).
* **Test doubles**: stand-in parts (the demo CRM, the demo mail system, the pre-written AI replies) used only in tests and demos.
* **CRM dump**: the list of records the demo CRM holds, read back from `/fake/crm`.
* **Host and Origin check**: the desk refuses web requests that name a wrong address or come from another web site.
* **UNKNOWN**: the desk is not sure whether a follow-up email left; it does not resend, and a person must check.
