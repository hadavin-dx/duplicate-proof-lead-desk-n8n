# Words used in this folder

Every word the other files use as a label is explained here once. Each file that uses a label points to this file the first time. (Moved out of `README.md`; no definition was dropped, several were added.)

## The test and its parts
* **Harness**: the set of Python scripts in `harness/` that starts n8n and the fake servers, sends the requests, kills n8n, counts the results and writes the tables. It is the measuring tool, not n8n.
* **A person or program that runs the harness**: whoever reruns it (a human or an AI agent). **The author** is the author of this folder; it wrote the harness and the rules and measured the published numbers.
* **The 2026-11-09 Windows run** (also "the published run"): the one automated run on one Windows 11 laptop whose raw files are in `published_run/` and whose counts are in `tables.md`.
* **Earlier rerun** (or "the earlier same-computer rerun") and **loaded run**: besides the published run the author made two unpublished runs on that same Windows laptop, neither independent and neither in this folder. (Besides those two full runs there was a short development test run of the rerun harness, described in `DETAILS.md`; it is not one of them and has no results of its own.) The loaded run was made before the earlier rerun, on a heavily loaded computer, and gave different counts for variant a and for the crashed-entry visibility; the earlier rerun was made on a computer that was idle at its start, and the rule's lists were drawn after the author had seen it (`REPRODUCTION-RULE.md`, top).
* **FIX1** and **lead ruling**: old labels inside `CHANGES-FROM-ORIGINAL.diff` and one assertion string; they mark the author's first batch of changes and an earlier decision of the author, with no other meaning.
* **Outside read**: a review of this folder by a reader other than the author, whose remarks led to edits (for example polling instead of fixed waits). The edits are listed in `CHANGES.md`.
* **Lead**: one made-up person (a name and an e-mail address) sent to an n8n workflow by an HTTP request. ("Lead ruling" in a label quoted in `DETAILS.md` is an old label for the author's own decision: "lead" there means the author, not a third person, and is not this word.)
* **Variant**: one workflow design. **a** is n8n's Remove Duplicates node with default settings. **b** is a Postgres node doing `INSERT ... ON CONFLICT DO NOTHING RETURNING`, then a branch on "a row came back". **c** is a Data Table upsert, then a branch on "created time equals updated time" (a derived signal: the node gives no inserted-or-existed flag). **d** is the same workflow file as a, run with the n8n setting `N8N_CONCURRENCY_PRODUCTION_LIMIT=1` (one request at a time, so it cannot race). **e** is variant b plus a status column (`pending`, `sent`) and a second workflow that runs every 15 seconds and re-sends pending leads. The files are in `workflows/`. The Postgres nodes there carry no credential on purpose (the scrub removes it); the run creates its own.
* **CRM**: the fake customer-record server. **Mail**: the fake mail server. Both are one small program, `harness/fakes2.py`, together called the **stand-in**; it counts every post and cannot recognise a repeat. All data is made up. The stand-in's mail part is "blind" in variant e: it stores every email it is sent. **Stand-in log**: `calls2.jsonl`, the stand-in's own record of every post it received.
* **IF node**: an n8n node that sends an item down one of two branches by a condition (variants b and c use one to tell "new lead" from "already seen"). A wrong setting in that node made 20 attempts of c invalid.
* **Remove Duplicates node**: a built-in n8n node that drops items it has already seen. **Data Table**: a built-in n8n table store with an upsert (insert or update) operation. **SQLite**: the small file database n8n uses inside itself by default. **Queue mode**: an n8n setting in which separate worker processes run the executions; it was not used here. **Task runner**: the helper process n8n starts to run code nodes (its port, 5780, is one of the ports the harness needs free).
* **Executions listed**: the executions n8n reports through its HTTP API for one workflow. **Crashed entry**: an execution that n8n lists after the restart with status `crashed`, `error` or `failed`. **Retry pressed**: the harness calls n8n's retry (`POST /executions/<id>/retry`, with the stored original workflow) once for each crashed entry (the call behind n8n's Retry button). **`retry_responses`**: the field of a raw result row that holds n8n's replies to those retry calls; it is not copied into `tables.md`.
* **Run**: one try with a new made-up address. (The prefix `wp0b` in workflow names and in the made-up test addresses is just a label from the run day.) **Valid run**: a run that meets the rule for being counted (n8n listed ten executions and all ten were alive at the same instant; for variant d: ten sent within 100 ms and ten listed; for a kill run: the held request was seen, a process was killed and n8n restarted). **Invalid attempt**: a run that did not meet that rule; it is kept and counted, never dropped (see "Attempts" in `tables.md`). **Harness fault**: the harness or a workflow it deployed was wrong or not ready (for example a wrong setting in an IF node); such attempts are kept and counted and are not results.
* **Barrier**: the ten requests of a run are all made ready first and released at the same instant (a thread barrier), so they start together.
* **Settle wait**: the time the harness waits after a run for the counts to stop changing. It is not a fixed time: the harness polls until no new post reached the stand-in for 3 seconds (`DETAILS.md`, "How a run works").
* **Overlap**: the ten executions of one run were alive at the same instant, so the race could happen.
* **Replay**: the same ten requests sent again as soon as the first ten are quiet.
* **Claim step**: a row written in the database before any outside call, saying "this lead is being handled" with a time, so that after a crash a restart can find unfinished claims and resume or release them. Variant b's insert only records that the lead was seen and keeps no progress, so it is not a claim step in this sense; a claim step was not tested.
* **Sending state**: a status such as `sending` written to the database **before** the e-mail request leaves, so that a restart can tell "not sent" from "may have been sent". Variant e has `pending` and `sent` only; a `sending` state between them was not tested.
* **Sweeper / re-send job**: the second workflow of variant e.

## Kills
* **Kill**: ending the n8n process (and its helper processes) with the operating system's kill, in the middle of a run. A kill **fails** if the process did not die; then the run is invalid. **Lost connection**: a client of the ten at once saw its connection closed by the kill (the error names are in `harness/summarise.py`, `LOST_CONNECTION`). "No lost connection seen" in a kill run means the kill may have had no effect.
* **Kill points** are the moments at which n8n is killed during a run; **K1, K2, K3** are their names in the raw files. They mean **different moments for variants a to d and for variant e**, so the tables name the moment in words:

| Raw file | K1 | K2 | K3 |
|---|---|---|---|
| `g3_a`, `g3_b`, `g3_c`, `g3_d` (variants a to d; steps: CRM, then email) | email request in flight (CRM already stored) | email stored, its reply held 3 s | CRM request in flight, first step (the email is never sent) |
| `g3e_K1`, `g3e_K2`, `g3e_K3` (variant e; steps: email, then CRM) | CRM request in flight, last step (email already sent, status `sent`) | email stored, its reply held (status `pending`) | email request in flight (status `pending`) |

* **`stale_running_after_kill`**: a field of a raw kill row, true when n8n still listed an execution as running after the restart although its process had been killed.
* **Process group, SIGTERM, SIGHUP, SIGKILL, nohup, setsid**: a process group is a set of processes that one signal can reach together. SIGTERM asks a process to stop and can be handled; SIGKILL ends it at once and cannot be handled; SIGHUP is sent to a terminal's processes when the terminal goes away (an ssh session dropped). `nohup` starts a command so that it ignores SIGHUP; `setsid` starts it outside the terminal's session. **isolated-vm**: a native add-on that n8n uses to run code nodes; `npm rebuild isolated-vm` compiles it, which needs a C++ compiler.
* **Multi-arch index and digest**: a Docker image can be named by the SHA-256 of its content (its digest); a multi-arch index is one such name that lists one image for each CPU type (x86-64, arm64).

## The rules
* **Test configuration**: one value of the `setup` column in `load.jsonl`, for example `a default`, `d limit1` or `b kill runs K2`. The tables name the same things in a different form (and one table row for the kill runs of a variant stands for three of them); the list of the forms is in section 1 of `REPRODUCTION-RULE.md`.
* **Pass**: met the author's own rule (`GATES.md`). **Gate**: one pass rule (G1, G2, G3 in `GATES.md`); the word is used for nothing else here. The **idle check** is the separate rule that the computer must be idle before every test (the option `--gate-wait-min` and the row name `load_gate_failed` belong to the idle check and keep their old names).
* **List M**, **list T**, **R1**, **R2**, **M1 to M5**, **T**: the names used in `REPRODUCTION-RULE.md`. M1 to M5 are the five counts a rerun must match; list T holds the counts that move with timing and are only quoted; R1 and R2 are the two rules that say when a count is scored. They are explained there, in sections 1 to 3.
* **SHA-256**: a fingerprint of a file; it can only confirm later that a file is unchanged, it is not a timestamp.
* **Wilson interval**: a standard way to give a 95 percent range for a share such as 18 of 20 (the Wilson score interval). The runs here are not independent, so the ranges in `tables.md` are too narrow (see there).
