# When a rerun counts as "reproduced"

**Where this rule comes from, and what it is worth.** It was drafted by the author of this folder, using the earlier rerun (`GLOSSARY.md`: one of two unpublished later runs on the same Windows computer that produced the published tables). That earlier same-computer rerun was **not** independent, so it is not evidence of reproduction by someone else. **No independent rerun result existed when this file was last edited (2026-11-14)**; the author states that, and it cannot be checked from this repository (the hash in `SHA256SUMS` shows what the file says now, not when it was written). **The list of counts in section 2 was chosen from the counts that matched in that earlier rerun.** That is selecting the test after seeing the outcome: that the earlier rerun "passes" this rule shows nothing about the rule, and the rule has not been tried on any rerun it was not drawn from. If this file is changed after a rerun result has been read, the change must be dated and say so.

Any later edit needs its own dated line here.

The published tables are `tables.md` (counted from the files in `published_run/`). A "rerun" is a full run of `harness/run_all.py` (not `--smoke`) followed by `harness/summarise.py` on its results, as written in `README.md`.

## 1. What "reproduced" can be said about

Only about one count at a time, never about the whole folder. A rerun can reproduce one count and fail to reproduce another. **Who scores:** the person or program that runs the harness scores its own rerun with this file and publishes the counts, `run_manifest.json` and `load.jsonl`; nobody else checks the scoring unless they redo it from those files.

**Test configurations are scored one by one.** A *test configuration* is one value of the `setup` column in `load.jsonl`: one setting of one variant (for example `b default` or `d limit1`), or the kill runs of one variant at one kill point (for example `b kill runs K2`). **The tables may merge three of them in one row** (the row "X (kill runs)" stands for `X kill runs K1`, `K2` and `K3`). The names appear in three forms. `load.jsonl` of a full run: `a default`, `b default`, `c default`, `d limit1`, `a kill runs K1` to `K3` (the same for b, c, d) and `e kill runs K1` to `K3`. The tables (`summarise.py`): "X default (ten at once)" and "d limit1 (ten at once)" are `X default` and `d limit1`; one row "X (kill runs)" per variant a to d stands for that variant's three `X kill runs K1`, `K2` and `K3`; one row "e K1 (kill runs)" per point is `e kill runs K1` (and likewise K2, K3). A `--smoke` run (variant b only, not a reproduction) writes `b kill runs` without a suffix for K1, then `b kill runs K2` and `b kill runs K3`. A count from a busy test configuration (section 5) is not scored, and the counts from the other test configurations of the same run are scored on their own. **(R1) A count that combines several test configurations (M4 and M5) is scored only if every test configuration it uses is not busy.** M1, M2 and M3 are scored per test configuration. **How to write a busy case:** if only `b default` was busy, "M1 reproduced for c and d; not scored for b; run labelled not clean" is the correct wording (section 5). A count that fails R2 does not take other counts with it: if `d limit1` has only 18 valid runs, M1 is "18 of 20 valid, no claim" for d only, and M1 for b and c is still scored.

## 2. Counts that must match (list M)

**(R2) Every M count needs the full number of valid runs behind it: 20 per ten-at-once test configuration, 5 per kill point.** With fewer (exit code 2, or `summarise.py` printing SHORTFALL), quote "k of n valid" and make no reproduced or not reproduced claim for that count.

Each count below is reproduced if and only if the rerun's own number is **equal** to the published one; otherwise say "not reproduced" for that count and quote the rerun's number. There is no "close enough". The test configurations that hold each count are named after it.

* **M1** Ten at once, variants **b, c and d** (valid runs only): the number of runs ending with exactly one CRM row and one email (published: 20 of 20 each). A valid run of d is judged by the relaxed rule (ten sent within 100 ms and ten executions listed; `DETAILS.md`, "Rules and honest notes on how the test was set"). Test configurations: `b default`, `c default`, `d limit1`.
* **M2** Replay, variants **a, b, c and d**: the number of runs where the replay added posts (published: 0 of 20 each). Only "the replay added nothing" is compared, as a count; the replay is sent as soon as the first ten are quiet, so its timing differs (about 3 s in a rerun, about 5 s in the published run; this is disclosed in `tables.md` under the replay heading), which means the two replays are not quite the same test. The rule scores only the equality of the 0-of-20 count and does not compare timing, so "0 of 20 in both" is a weaker statement than the same timing would give. Test configurations: `a default`, `b default`, `c default`, `d limit1` (the replay is part of the same run as the ten).
* **M3** Kill runs of variants **b, c and d**: the final (CRM rows, emails) for each kill point, as a set of counts (for example "5 of 5 at (1,1)"), one variant and one kill point at a time. Always report M5 for the same variant beside M3: if M5 is not 0 of 15 there, the kills may not have taken effect and M3 for it says little. If the harness gives up on a kill row (it did not see the held request, no process was killed, n8n did not restart), that row stays in the file as not valid and is never repeated; fewer than 5 valid rows at that kill point means R2 applies (no claim for that count; the run ends with exit code 2). **Worked non-match:** published "5 of 5 at (1,1)" at the point "email request in flight" for variant b; a rerun with "4 of 5 at (1,1) and 1 of 5 at (1,2)" is **not reproduced** for variant b at that kill point (one different run is enough); variant b at its other kill points, and variants c and d, are scored on their own. Whether the crashed entry was visible is **not** in this list (see section 3). Test configurations: `b kill runs K1`, `b kill runs K2`, `b kill runs K3`, `c kill runs K1`, `c kill runs K2`, `c kill runs K3`, `d kill runs K1`, `d kill runs K2`, `d kill runs K3`.
* **M4** is **three counts for variant e**, each reported on its own: (i) the number of runs that ended with two or more emails at the two email points (published: 10 of 10); (ii) the number of kill runs whose status was not `sent` at 60 seconds (published: 0 of 15); (iii) the final counts of the point "CRM request in flight, last step" (published: 5 of 5 at (1,1)). Never write "M4 reproduced" as one statement. Test configurations: `e kill runs K1`, `e kill runs K2`, `e kill runs K3`. By R1, count (i) uses two of them (K2 and K3), count (ii) uses all three, and count (iii) uses only K1: a busy test configuration makes only the counts that use it unscored.
* **M5** Kill runs in which no client saw a lost connection, per variant a to d (published: 0 of 15 each; it says whether the kill took effect). The count is over the **valid** kill rows only (`summarise.py` prints "of N valid kill rows"); a row that the attempts list calls invalid is not in it. Test configurations: `X kill runs K1`, `X kill runs K2` and `X kill runs K3` for the variant X. By R1, the 15 rows come from three test configurations: one busy one means M5 is not scored for that variant.

## 3. Counts that move with timing (list T)

These differed between the published run and the earlier rerun, or depend on a race. **Never** say "reproduced" or "not reproduced" about one of them. Quote the rerun's number with the words "in this rerun", or quote a range that contains both numbers.

* **Variant a, ten at once:** the number of runs ending with more than one CRM row or email (published: 2 of 20 with more, 18 of 20 at (1,1)), and the size of a bad run (published (3,3) and (8,8); the earlier rerun had (2,2)). So "17 of 20 at (1,1)" is **not** "not reproduced": it is quoted as "17 of 20 in this rerun".
* **Variant a, kill runs** (all three kill points): the final counts and visibility. A kill run of variant a in which several CRM posts had already been made at the moment of the kill says nothing about a crash.
* **Crashed-entry visibility at every kill point and for every variant: quote only** (for the "email request in flight" point it was 4 of 5 in the earlier rerun and 5 of 5 in the published run). The same holds for the list of executions after the restart and for the number of retry presses.
* How many CRM rows a second re-send run of variant e produced (2 to 4 of 10 were seen), the variant e ten-at-once counts, and the final counts of variant e at its two other kill points that are not named in M4.
* The gaps, in milliseconds, between two re-send emails less than one second apart.
* Execution times, the split of 200 and 500 replies, and the number of invalid attempts.
* **A count in neither list (M or T):** quote the rerun's number with its variant; make no reproduced or not reproduced claim.

## 4. What the exit code means

Exit code 0 of `run_all.py` means: every test configuration has the expected number of valid runs. It does **not** mean that the counts match the published ones. Compare the counts yourself.

## 5. A run that is not a clean reproduction

* A run made with `--min-idle 0` has the idle check switched off. It is NOT a clean reproduction, and anything published about it must say so, quote `min_idle` from `run_manifest.json`, and include `load.jsonl`. Its counts are scored as usual (section 1) and are always published with this not-clean label.
* **A busy test configuration.** `load.jsonl` has one JSON object per line: `ts` (time, UTC), `setup` (the name of the test configuration, for example `a default`, `d limit1`, `b kill runs K2`, `e ten at once`), `when` (`before`, `during`, `after` or `load_gate_failed`), `cpu_idle_pct` and `free_ram_mb`; a row with an `error` key and no `cpu_idle_pct` is not a reading. A test configuration is *busy* if its readings (every row of that `setup` that has a `cpu_idle_pct`, including its `before` and `after` rows, in file order) hold **two or more consecutive readings with CPU idle below 80 percent**, **or** if their average is below 80 percent. `python3 -I harness/summarise.py <work folder> --ext jsonl --busy` prints this verdict, one line per test configuration, with the average to two decimals (79.96 is not shown as 80.0). A single reading below 80 does not make a test configuration busy, but it must be quoted; the exception is a test configuration with only one reading, which is judged by its average, that is, by that reading. A row whose `cpu_idle_pct` is not a number (NaN) is unreadable: `--busy` refuses it with a one-line message instead of reading it as quiet. The same holds for infinity (`1e999`) and absurdly large numbers in any raw result file: `summarise.py` refuses the file in one line. If `load.jsonl` has no readings at all (missing, empty, only error rows), the load is **not judged**: quote that and publish the run with the not-clean label. A run with any busy test configuration is labelled NOT a clean reproduction, **but each count whose test configurations were not busy is still scored** (section 1); you may write "M1 reproduced for c and d; not scored for b; run labelled not clean" (section 1). *Consecutive* means two readings of the same `setup` that follow each other in file order. **The basis for this rule is the author's report, not checkable here:** the author reports the loaded run (`GLOSSARY.md`: an unpublished run on a heavily loaded computer, made before the earlier rerun) that gave different counts for variant a and for the crashed-entry visibility, and says they went back to the published values when the computer was not loaded. That run is unpublished and is not in this folder. Treat it as the reason to label busy runs, not as a measured effect. A test configuration that has no readings while others in the same `load.jsonl` have some (only error rows) is not judged: `--busy` prints "no readings" for it and it counts as not clean.
* A run that ended with exit code 2, 3, 130 or 143, or whose `run_manifest.json` says anything other than `finished`, is not a reproduction as a whole and must be called incomplete. The counts of test configurations that finished complete and were not busy are scored one by one (section 1).

## 6. What a rerun must record

Anyone who reruns this and says "reproduced" or "not reproduced" must record and publish together with the counts:

1. who ran it: a person or an AI agent (and which);
2. the operating system and machine type;
3. the file `run_manifest.json` from the work folder (versions of n8n, Node and Python, the git head of the harness, the load at the start and at the end), and the output of `git rev-parse HEAD` of the cloned repository;
4. the file `load.jsonl`. **Read `run_manifest.json` and `load.jsonl` before you post them: they may show details of your machine (operating system, versions, load);**
5. for each count of M1 to M5: equal or not, with the rerun's number (M4 has three counts, each judged by R1 on its own test configurations: report each one); and the rerun's number for every item in section 3 and for every other count that you quote, with the variant named (a number without its variant cannot be sorted into M or T).

**Where to publish.** Anywhere the rerunner likes that others can read, for example an issue on the repository named in `README.md` (step 1; its location may change, so a page of your own is a safe choice) or a page in the rerunner's own repository, with `tables.md`, `run_manifest.json` and `load.jsonl` attached and the name of who ran it (a person or a program). Nobody needs the author's permission or reply.

## 7. What a reproduction does not show

A reproduction shows that the same small test, on another computer, gives the same counts for list M. It does not show anything about other n8n versions, queue mode, several n8n processes, real CRM or mail services, other loads, or any other tool.

## 8. Worked example: the earlier rerun on the same computer

This is how the rule above scores the written summary of that earlier rerun (same Windows computer, so not independent). **That earlier rerun's written summary, its `load.jsonl` and its `run_manifest.json` are not in this folder** (the author did not publish them), so you cannot check this example or that lists M and T were drawn from it; the table below, copied as counts, is the only record used. For the same reason the load is *undecided* for this example, by design (nothing in this folder says the computer was idle). The counts:

| Count (earlier rerun's summary) | Earlier rerun | Published |
|---|---|---|
| Variants b, c, d, ten at once: runs with exactly 1 CRM row and 1 email | 20 of 20 each | 20 of 20 each |
| Variants a, b, c, d, replay added posts | 0 of 20 each | 0 of 20 each |
| Variant e, kill runs at the two email points: two or more emails | 10 of 10 | 10 of 10 |
| Variant e, kill runs not `sent` at 60 s | 0 of 15 | 0 of 15 |
| Variant e, kill at "CRM request in flight, last step": final (CRM rows, emails) | 5 of 5 at (1,1) | 5 of 5 at (1,1) |
| Variants a to d, kill runs with no lost connection seen | 0 of 15 each | 0 of 15 each |
| Variants b, c, d, kill runs: final counts | "identical to each other" (no counts given) | see `tables.md` |
| One kill run, variant not named, at "CRM request in flight, first step": final | (10,0) | not applicable |
| Variant a, ten at once: runs at (1,1); size of the bad runs | 18 of 20; (2,2) | 18 of 20; (3,3) and (8,8) |
| Crashed entry visible, "email request in flight" point | 4 of 5 | 5 of 5 |
| Variant e, runs with a second CRM row | 2 of 10 | 4 of 10 |
| Variant e, gaps between two re-send emails | 48 and 56 ms | four gaps of 52 to 63 ms |
| Load | idle at the start (the summary does not say more), one reading at 100 percent CPU use mid-run | not applicable |

* **M1, M2, M4, M5:** every listed count equals the published one. Each is "reproduced", conditional on a clean run (section 5, undecided below).
* **M3:** **undecided**: the summary gives no counts for the kill runs of b, c and d (only "identical to each other"), and the one run that ended at (10,0) has no variant name, so M3 cannot be scored for any variant from this record. Section 6 item 5 requires the variant with every number.
* **List T, "quote the rerun's number":** the variant a, visibility, second-CRM-row and gap rows of the table.
* **Load (section 5):** one reading is not "busy", but the average of the test configuration that held it is not in the summary, so whether that rerun was clean is **undecided** until its `load.jsonl` is read. The definition in section 5 gives the number of readings, so two readers apply it the same way.
* **What the example shows:** the earlier rerun's count of 18 of 20 for variant a is not a "match" under this rule (it is list T); and the rule could not score one of its kill runs because the summary did not name a variant.

**Three short worked cases** (invented numbers, for the method only).
1. *A busy configuration.* `load.jsonl` shows `b default` with readings 95, 70, 72, 96 (two in a row below 80: busy) and every other reading 80 or above. Write: "M1 reproduced for c and d (20 of 20); not scored for b; run labelled NOT a clean reproduction." M2 is scored for a, c and d; for b it is not. M4 and M5 are scored for every variant whose test configurations were all not busy (they use the kill configurations, so a busy `b default` does not block them for b).
2. *An R2 shortfall.* `d limit1` has 18 valid runs, and 17 of those 18 valid runs ended at (1,1). Write: "M1 for d: 17 of the 18 valid runs ended at (1,1); no claim (R2)." M1 for b and c is still scored; the run ends with exit code 2 and is called incomplete as a whole.
3. *M4 with one configuration unscored.* `e kill runs K3` was busy, K1 and K2 were not. Count (iii) (K1 only) is scored; count (i) (K2 and K3) and count (ii) (all three) are not. Write each of the three counts separately, with "not scored" for the two.
