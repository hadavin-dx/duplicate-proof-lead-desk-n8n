# Details: what was run, how the test was set, results notes, how a run works

(Moved out of `README.md`, with these exceptions: the estimate of about 1.5 to 2 hours without the smoke run, the remark that a commit hash cannot be written into the files it hashes (so none is pinned), the pass rule's "at most one" explanation inside the study question, the old shell loop for cleanup (replaced by `harness/cleanup.py`), and shorter wording in several steps. Every number and caveat of the results is kept. Terms are explained in `GLOSSARY.md`.)

## What was run (versions as measured)
| Item | Value |
|---|---|
| n8n | 2.46.6 (installed from `package-lock.json`), regular mode (no queue), one process, SQLite inside n8n |
| Node.js | 24.22.2 (n8n 2.46.6 refuses older Node), npm 11.19.1, Windows x64 |
| Postgres (variants b and e) | image `postgres:16` in Docker; the digest used is in `harness/run_all.py` (`PG_IMAGE`); it was the same image as on 2026-11-09 |
| Ports on 127.0.0.1 | 5679 (n8n), 5780 (n8n task runner), 8790 (stand-in server), 55432 (Postgres) |
| Machine | one Windows 11 laptop |

The published numbers are from **Windows x64**. The harness also supports **Linux** (x86-64 and arm64; the pinned Postgres image digest is expected to be a multi-arch index but that was **not verified for arm64**, so an arm64 run may fail at the image pull); that part was written on Windows and has **not been run on Linux yet** (it is exactly what an independent Linux rerun is for). macOS is not covered. n8n installed through Docker is **not supported** by the harness: it needs `node_modules/n8n` from `npm ci` and a process it can kill, so use the npm install described in `README.md` (the Postgres container is the only Docker use).

## Rules and honest notes on how the test was set
See `GATES.md` (the pass rules in plain words). **The original rule file is not published** (a private document of the author, which also holds other notes). Its SHA-256 is recorded in `gate-rule.sha256.txt`, which names the withheld file `gate-rule-original.md`; that file is not in this folder (the fingerprint proves nothing about when it was written or what it says), and a plain-words summary of the rule is in `GATES.md`; treat that summary as the author's word, since nobody can compare it with the file. The author states that the rules were written before the results were read; that cannot be checked from this repository. How a rerun is judged is in `REPRODUCTION-RULE.md`.
* The rule has two kill points. The third one (the CRM request in flight, the first step, so no email is sent) was **added by the author after the rule was written down** (the author's own account).
* For variant d the rule for a valid run was changed during the run (a variant that runs one request at a time can never overlap): the **relaxed rule for d** says valid = the ten were sent within 100 ms and n8n listed ten executions. The 20 published rows of `g12_d_limit1.ndjson` carry the label `valid under lead ruling for serialised variant`: that is the old name of the relaxed rule for d ("lead ruling" was an old label for the author's own decision). The rows are published as they were written, so the label is not edited (it would break the "no count was edited" claim); new runs write `valid under the relaxed rule for d (serialised variant)`.

## Results notes
The counts are in **`tables.md`**, generated from the raw files in `published_run/` by `harness/summarise.py`; `README.md` repeats only the headline. Its first section is a summary; the rest are the per-run tables, the Wilson 95 percent intervals and a cross-check of each run's final counts against the stand-in server's own log. Read these before quoting anything:
* **Variant a** is the only variant where duplicates were seen in the ten-at-once runs (2 of 20); we did not investigate why. One kill run of variant a already had several CRM posts at the moment of the kill, so that run says nothing about a crash.
* **CRM request in flight (first step)**, variants a to d: after one press of n8n's retry on each crashed entry, the final state is one CRM row and no email. n8n listed the crashed entry and the retry entry said `success`; no email was sent. **The cause was not investigated; it may come from how these test workflows are set up or from n8n itself**, so this is not a claim about n8n in general. Retry was pressed with the stored original workflow ("load workflow" off); other retry options were not tried.
* **Variant e**: no lead was lost, but the runs where the first email had already left ended with two or more emails, and some also with two CRM rows (two re-send runs about 50 to 65 ms apart; the cause is a guess, not verified). That is a finding about this design; no pass/fail rule applies to e. 11 attempts at e were invalid (5 + 1 + 5: the re-send job had an error, so the first attempts did not count) and are kept in `published_run/invalid/` and listed in `tables.md`, "Attempts". The raw file for e at the "email stored, reply held" point holds one invalid line (the evidence text of the time said two; the raw file is what counts).
* **Variant d kill runs:** 17 attempts, 15 valid; the 2 invalid attempts (`tables.md`, "SETUP PROBLEM retry not pressed": retry was not pressed) are kept in `published_run/invalid/` and are not counted.
* Duplicate callers in a to d got HTTP 500 "No item to return was found" while n8n's execution list said `success`. **The cause was not investigated; it may come from how these test workflows are set up or from n8n itself.**
* **A kill can fail to take effect.** The published run recorded only that the harness found an n8n process to kill (`killed_pid`), not that the process died; the rerun harness records a kill only when the operating system reported success and port 5679 was free again afterwards. In a short test run of the rerun harness on a busy computer (a development test, not one of the two unpublished full runs of `GLOSSARY.md`), one kill run of variant b did not take effect (the client got a normal answer, no crashed entry appeared, the lead ended with one CRM row and one email); the cause was not found. `tables.md` counts, per variant, the kill runs in which no client saw a lost connection; such a run is not a counter-example to anything. A kill run with `killed_pid` true but no lost connection is still valid and counted. Run the test on an otherwise idle computer.
* The stand-in server stores a request that is already inside its 3-second hold even after n8n has been killed. So an "email in flight" kill always ends with the email stored by the stand-in, which n8n never learned of.

**Not tested:** queue mode, several n8n instances, other n8n versions, other kill timings (for example n8n dying before the email request leaves n8n), kills of Postgres or of the stand-in servers, a mail stand-in that recognises repeats for variant e, the re-send job overlapping a slow main run, n8n's other retry option, any real mail or CRM service, loads above ten, Linux and macOS. No other tool was compared.

## What `run_all.py` does
* **What it starts.** A Postgres container named `n8n-publish-pg` (label `n8n-evidence.run=1`), the stand-in server and one n8n process. It generates a random owner account and database password (kept in `<work>/.run/`, never printed), runs every test in the order of the original run, and stops only what it started: the process groups it recorded in `<work>/.run/pids.json` and the container it created. It never ends whatever happens to hold a port (the same holds for `harness/cleanup.py`, which ends a recorded process only if it started in this work folder and leads its own process group, and is the recorded program: node or python). n8n and the stand-in server get an explicit minimal environment (system folders, a short PATH, the n8n settings), not the parent's.
* **What it refuses.** It refuses to start in a folder that already holds results, if a port is in use, or if a container with the label `n8n-evidence.run=1` already exists. The single-script runners (`g12.py`, `g3.py`, `g12e.py`, `g3e.py`) refuse to append to an existing result file.
* **The idle check.** Before every test the computer must be idle: `run_all.py` waits up to `--gate-wait-min` minutes (default 10) for the CPU idle percent to be at least `--min-idle` (default 80). If that never happens it writes `load_gate_failed` to `load.jsonl` and exits with code 3. Machine load (CPU idle percent, free RAM) before, during and after every test goes to `load.jsonl` and is printed in the tables. `--min-idle 0` turns the check off; a run made that way is NOT a clean reproduction: say so in anything you publish, quote `min_idle` from `run_manifest.json` and include `load.jsonl`. The idle check looks at the CPU only (not memory or disk), so a busy computer is much less likely to produce quietly wrong numbers, but not impossible. The author's report that load changes counts is in `REPRODUCTION-RULE.md`, section 5 (it cannot be checked here).
* **Smoke run.** `--smoke` runs variant b only with 3 runs per test and also writes `smoke_readiness.json` (raw probes: how long the real webhook needs after n8n's readiness check answers).
* **What it writes into the work folder.** `g12_*`, `g3_*`, `g3e_*`, `g12e.jsonl` (raw results), `calls2.jsonl` (the stand-in's log), `load.jsonl`, `run_manifest.json`, `master_*.out` (the output of every step), `n8n2.log`, `fakes2.log`, `pull.err` (only if the Postgres image pull had to be retried), `ids.json`, `n8nhome/` and `.run/`. `run_manifest.json` records the n8n, Node and Python versions, the git head of whatever git repository holds the harness folder (`null` when git is missing or the folder is not in a repository), whether tracked harness files were modified, the operating system, the 404 wording in use, the load at the start and at the end, and how the run ended. Read it before you post it: it may show details of your machine. `data/` and `.run/` are git-ignored.

## How a run works
Each run uses a new made-up address; ten POSTs are fired together from behind a barrier with different request ids and the same address (then, for the replay, the same ten again as soon as the first ten are quiet).

The harness does not wait a fixed time: it polls until no new post reached the stand-in for 3 seconds, every listed execution is finished and the stand-in holds no request (at most 60 seconds; a timeout is written into the row and the run does not count). A run counts only if n8n lists ten executions that were alive at the same instant (variant d: sent within 100 ms). `tables.md` prints for every test the number of attempts, valid runs and every invalid reason; `summarise.py` exits with code 2 and prints SHORTFALL when a test has fewer valid runs than expected (`--runs`, `--kills`, `--variants`, `--no-e` set the expectation for a smoke run).

For a kill run, the stand-in holds one request for 3 seconds. The harness kills the n8n process group whose id it recorded when it started it, when it sees the request inside the hold. It then waits until the stand-in holds no request and the counts stand still, restarts n8n, waits for the crashed entry, presses retry once per crashed entry and reads the counts once the retried execution is finished and quiet. A kill run counts only if the held request was seen, a process was killed and n8n restarted. On Windows the harness kills with `taskkill`; on Linux it sends SIGKILL to the process group.

The samples of variant e at 5, 15, 25, 40 and 60 seconds are observation points of a re-send job that runs every 15 seconds, not settle waits.

**Comparing with the committed tables.** The rule for calling a rerun "reproduced" is in `REPRODUCTION-RULE.md`: a count is scored only when the full number of valid runs stands behind it (20 per ten-at-once configuration, 5 per kill point) and only when the test configurations it uses were not busy (rules R1 and R2 there); the rule also says where to publish your result and what to record. Some counts (the ten-at-once and replay counts, the kill-point final counts) are expected to match; counts that depend on timing (the split of 200 and 500 replies, the number of duplicate runs of variant a, execution times, how many of the re-send runs overlapped, the number of invalid attempts) may differ from run to run. The kill-count lines read "Kill rows where no client lost its connection: X of N valid kill rows (the result file holds R rows; M more attempts kept in invalid/) ... Rows with killed_pid not true in the raw row: Y" (the part about `invalid/` appears only for attempts the original run moved to `published_run/invalid/`); in the published rows `killed_pid` only means a process was found. The count is over valid kill rows only, the rows that `REPRODUCTION-RULE.md` M5 uses.

## Rerun notes (Linux)
* **ssh drops.** **`nohup`** makes the process ignore SIGHUP, and `run_all.py` leaves SIGHUP ignored when it was already ignored, so the run simply goes on. **`tmux`** keeps the terminal alive, so no SIGHUP is sent. **`setsid`** (put it in front of `python3`) starts the process outside the terminal's session. With none of the three, SIGHUP (and a `timeout`'s SIGTERM) makes `run_all.py` stop cleanly with exit code 143 after running its cleanup; SIGKILL cannot be caught. The shell variables `h`, `node` and `work` exist only in the shell where you set them: in every new shell (a new `tmux` window, a reconnect) set them again first (`h=demo_only/n8n_evidence/harness`, `node=` and `work=` as in the README steps; `python3.12` instead of `python3` if that is what you installed), then run `python3 -B -I $h/run_all.py --work-dir "$work" --node-dir "$node"` (without `nohup`, the `sh -c` wrapper and `&`) inside `tmux`. Inside `tmux` you see the exit code directly (`echo $?` right after the command ends).
* **Time estimate.** About 1.5 to 2 hours without the smoke run, 2 to 2.5 with it. Basis: the one measured duration is the earlier rerun on Windows, about 75 minutes with `npm ci` taking about 5 minutes there (a second, loaded run on that machine was also a full run, but its duration is not stated here); the published run was also a full run, but its duration was not recorded. The Linux figures (70 to 90 minutes for the run plus 15 to 20 minutes per `npm ci`) are the author's estimate and have not been measured on Linux; the longer `npm ci` is assumed because a Linux install may compile a native module (the `isolated-vm` package) that the Windows run did not, which is unmeasured.
* **Repository location.** The repository location may change; if the clone fails, look for the author's repository.
* **Tables of the published folder.** `--ext jsonl` on `published_run/` prints SHORTFALL and exits with 2, because its files end in `.ndjson`; use the default extension there.
* **SIGHUP.** A shell shows 129 for a process killed by SIGHUP; 143 is what `run_all.py` reports for SIGHUP and SIGTERM.
* **Where the results go.** Everything is written into the work folder `$work`: the raw results (`g12_*.jsonl`, `g3_*.jsonl`, `g3e_*.jsonl`, `g12e.jsonl`), `run_manifest.json`, `load.jsonl`, and, after step 7, `tables.md`; the output of the run is `rerun-1.out` next to the work folder.
* **Cleanup.** `run_all.py` refuses to start while an earlier container or process is left over (it says so). `harness/cleanup.py` removes what a hard-killed run left, using the process groups recorded in `<work>/.run/pids.json`; it prints each recorded pid and ends a recorded process only if it started in this work folder and leads its own process group, and is the recorded program, node or python (after a reboot a stored pid may belong to another program; that one is printed by program name and skipped). If `$work/.run/pids.json` does not exist, the run was stopped before it started any process: only the container can be left, and the docker line of step 8 removes it. A hard-killed work folder cannot be reused: the next run needs a new, empty work folder.
* **Python 3.12 on Ubuntu 22.04** (it has 3.10): `sudo apt-get install -y software-properties-common && sudo add-apt-repository -y ppa:deadsnakes/ppa && sudo apt-get update && sudo apt-get install -y python3.12 python3.12-venv`, then write `python3.12` wherever the README says `python3` (including `python3.12 -m venv`).
* **Docker daemon.** If `docker info` does not answer: `sudo systemctl start docker` (preferred); on a machine without systemd, `sudo dockerd &` and wait until `docker info` answers. The user must be allowed to use Docker: member of the `docker` group (log in again after being added), or rootless Docker with `XDG_RUNTIME_DIR` set. If the `docker` command is missing, `run_all.py` stops with a one-line message. After the smoke run, `python3 -B -I $h/summarise.py --keys "$smoke" --ext jsonl` prints the names of the errors the clients saw while n8n was killed.
* Node.js **24.22.2** is required: n8n 2.46.6 refuses Node 22. Run `npm ci` and `npm rebuild isolated-vm` with the Node 24 folder first on `PATH`.
* `lib.py` already sets `N8N_LISTEN_ADDRESS=127.0.0.1` and `N8N_RUNNERS_BROKER_PORT=5780` for n8n (they are in `n8n_env()`).
* Before `docker run` the harness pulls the pinned Postgres image by digest: up to 4 tries with 15, 30 and 60 s pauses, at most 300 s per pull (Docker Hub answered HTTP 429 on tag pulls). It does not retry when Docker is not installed or when the Docker client says it cannot connect to its daemon or may not use it; any other error (including a registry answer that Docker prefixes with "Error response from daemon:", such as HTTP 429) is retried. Docker's error text goes to `<work>/pull.err`, not to the console.
* **The wording of n8n's 404 for a webhook that exists but not for GET is not verified.** The harness treats a 404 whose text contains `not registered for` as "registered", and 502, 503 and 504 as "not ready". The `--smoke` run records the raw answers in `smoke_readiness.json`; if they differ, set `N8N_WEBHOOK_LIVE_TEXT` to the text the file shows, then start the real run (the text in use is recorded in `run_manifest.json`). `summarise.py --keys` prints the names of the errors the clients saw while n8n was killed or under the ten-at-once burst of variant e; a kill counts as seen by a client when one of `ConnectionResetError`, `RemoteDisconnected`, `ConnectionAbortedError`, `BrokenPipeError`, `IncompleteRead`, `URLError:ConnectionResetError` or `URLError:BrokenPipeError` appears. An error while the request is being sent is recorded as `URLError:` plus the class of its reason; other reasons (refused, timeout) do not count as a lost connection. Read the real names with `summarise.py --keys` after the smoke run.

## Rerun it on Windows x64 (PowerShell, from the repository root)
Same needs as the Linux steps, plus Docker Desktop; Node.js 24.22.2 as the Windows x64 zip from the official Node.js download site (check its SHA-256 against the `SHASUMS256.txt` next to it; unzip it anywhere).
```
$work = "data\n8n_evidence_run\rerun-1"
New-Item -ItemType Directory $work
Copy-Item demo_only\n8n_evidence\package.json, demo_only\n8n_evidence\package-lock.json $work
$node = "<folder that holds node.exe>"
Push-Location $work; & "$node\node.exe" "$node\node_modules\npm\bin\npm-cli.js" ci --no-audit --no-fund; Pop-Location
python -B -I demo_only\n8n_evidence\harness\run_all.py --work-dir $work --node-dir $node
python -B -I demo_only\n8n_evidence\harness\summarise.py $work --ext jsonl --out $work\tables.md
```
