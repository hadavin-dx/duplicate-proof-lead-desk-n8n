# The pass rules, in plain words

A "gate" here means one pass rule: G1 (ten at once), G2 (replay) and G3 (crash); the word is used for nothing else. "Pass" means "met the author's own rule". The author of this folder states that the rules were written down before the results were read; this cannot be checked from this repository.

**The original rule file is not published**: it is a private document of the author that also holds other notes. `gate-rule.sha256.txt` names it `gate-rule-original.md`; that file is not in this folder. A SHA-256 is a fingerprint of a file; it can only confirm later that a file is unchanged. The fingerprint of the withheld file is in `gate-rule.sha256.txt`; it proves nothing about when it was written, when anyone read results, or what it says. What it says, as far as it matters for the results, is summarised below in plain words. **Treat this summary as the author's word**: it is an account, not a copy, and nobody can compare it with the file.

How a rerun is judged is in `REPRODUCTION-RULE.md` (a separate file; it was drafted after one earlier rerun on the same computer, see its first paragraph).

* **G1, ten at once.** 20 valid runs per variant. Each run: a new made-up address, ten requests with different request ids and that address, fired together. A variant passes only if every run ends with at most 1 CRM row and 1 email and at least one run ends with exactly 1 of each. One bad run fails the variant.
* **G2, replay.** The same ten sent again about 5 seconds later add nothing.
* **G3, crash.** n8n is killed while a stand-in server is holding one request for 3 seconds, restarted, and n8n's retry is pressed once for each crashed entry. Pass: at most 1 CRM row and 1 email at the end, and the crashed entry is visible in n8n's list. The rule names two kill points: the email request in flight, and the email stored with its reply held. **A third point (the CRM request in flight, the first step, so the email is never sent) was added by the author after the rule was written down, according to the author**; the rule says nothing about it.
* **Valid run.** n8n must list 10 executions and all ten must be alive at the same instant (overlap). **For variant d (concurrency limit 1) this was changed during the original run**, because a variant that runs one request at a time (concurrency limit 1) can never overlap: valid means the ten were sent within 100 ms and 10 executions were listed. The first run of d produced 35 attempts that the original rule did not accept as valid; the original run rejected all 35 under the overlap rule and kept them in `published_run/invalid/`, and none is counted in any result. In the raw file one is a harness fault (HTTP 404, the webhook was not registered yet) and 34 have an empty execution list (0 executions listed, so the overlap test could not be applied; `tables.md`, "Attempts", shows the split; for information, those 34 ended with 1 CRM row and 1 email each). The relaxed rule (ten sent within 100 ms and ten executions listed) rejects all 35 as well, so none is counted anywhere; summarise.py recomputes validity from the rows and agrees.
* **Harness faults** (n8n failed to start, wrong setting; the raw file labels say SETUP PROBLEM) are repeated and kept, not counted as a fail.
* Variant e (a status column and a re-send job) was added later and has no rule of this kind: no pass/fail rule applies to e: it is reported as counts only.
