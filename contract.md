# contract.md

In this file "fake" and "recorded" are internal names for the demo stand-ins (`FakeCrm`, the `/fake/...` paths, `RecordedQualifier`): "fake = demo stand-in", "recorded = the pre-written AI replies".

This file is the single reference for the replies the desk and the fake servers give and the rules the tests check. Where code and this file disagree, that is a bug to report.

## Reply rows that are easy to miss (all already in the table below; repeated here as a checklist)

| Situation | Status | Body | `receipt_id` |
|---|---|---|---|
| Unknown route | 404 | `{"error":"not_found"}` | not present |
| Known route, wrong method | 405 | `{"error":"method_not_allowed"}` | not present |
| `GET /counts?expected=x` with x not an integer, or negative | 400 | `{"error":"bad_expected"}` | not present |
| Envelope broken (400) or body over the cap (413) | 400 / 413 | `{"error":"bad_envelope"}` / `{"error":"too_large"}` | `null` (no receipt exists) |
| Request the standard library cannot read (malformed request line, unknown method such as `TRACE`) | 400 / 501 | `{"error":"bad_request"}` / `{"error":"not_implemented"}` | not present |
| `HEAD` or `OPTIONS` | 404 or 405 | the same JSON as for any other unknown route or wrong method (a `HEAD` reply has the headers and no body) | not present |
| Lock wait over (or, on `/api/ui`, more than 8 requests at once) | 503 | `{"error":"busy"}` (a different shape from the connection-limit 503 above, which has `reason`) | the receipt id, or `null` if the receipt was not yet written |
| A connection limit is reached (reading places or handler threads) and no connection can be closed for room (any route) | 503 | `{"error":"busy","reason":"busy"}` with `Retry-After: 1` | not present (no receipt is written; sending the same request number again is safe) |
| Any other internal error | 500 | `{"error":"internal"}` | the receipt id, or `null` |
| Any 409 or `bad_decision` row (retry/resolve) | 409 / 400 | `{"error":"...","hint":"..."}` / `{"error":"bad_decision"}` | not present (these rows never carry `receipt_id`). In approval mode also `409 already_decided` (body: the six decision keys, no `hint`) and `403 not_an_approver` (resolve, see step 3a). |

The `Content-Type` header of a request is not checked: the body is read as JSON whatever it says (text/plain, a form type or a UTF-16 body are all accepted if the body parses as JSON). State once: only the POST /leads rows carry `receipt_id`. The 409 and `bad_decision` rows never carry it. A 503 from a lock wait, and 500, carry the receipt number, or `null` if the receipt was not yet written. 400 `bad_envelope` and 413 `too_large` carry `null`.

Input rules (the tests are in `tests/test_input_edge_cases.py`, `tests/test_desk_edge_cases.py`, `tests/test_desk_http_edge_cases.py` and the other `tests/test_*_edge_cases.py` files, `tests/test_stamp_locks_and_budget.py`, `tests/test_model_stamp_and_reaper.py`, `tests/test_claim_checks_and_crm_mode.py`, `tests/test_hung_model_call.py` and `tests/test_hung_adapter_calls.py`):
* (1) JSON nested so deeply that the parser gives up is a 400 `bad_envelope` (counted in `rejected_envelopes`), not a 500; for `/resolve` it is a 400 `bad_decision`.
* (2) The stored copy of the payload escapes every non-ASCII character (`ensure_ascii`), so a JSON escape for half a character (a lone surrogate) is stored as text; a name, email, phone, company or message that contains one cannot be stored and gives verdict `review` with reason `bad_field:<field>`.
* (3) An email whose lower-case form is longer than 254 characters (some letters become two when lower-cased) gives verdict `review`, reason `invalid_email`, not a 500.
* (4) Only the thread that won the claim asks the AI step, the CRM or the sender, so two requests that drive the same new lead at the same moment, or a request and the reaper, ask the AI step once (the claim comes first; the reaper only drives `pending` rows, and a claimed row is `sending`); a CRM row can be put again only after a leftover intent mark, and then only on a keyed CRM, see the CRM row above.
  * A failed AI step after the claim is one automatic try (`internal:<class>`; the row goes back to `pending` with a backoff through `_abort_unsent`, and to `failed` only when the cap is already reached; after a person's Retry the count starts at 1, so the row is `pending`).
  * A lock on any write after the claim, the first stage stamp included, gives the try back instead (see the line on locks below), with one exception: a lock that stops the write of a model answer leaves the try used up (`ModelAnswerLost`, below).
  * The desk bounds every model call itself (`Desk._ask_model`): the call runs in a helper thread and the desk waits for it at most `MODEL_CALL_BUDGET_SECONDS` (9 s of real time), whatever the adapter declares; a qualifier that declares no `timeout_seconds` is accepted.
  * If the answer has not come the desk stops waiting, raises `ModelTimeout` (the follow-up goes back to `pending` with `internal:ModelTimeout` and a backoff, `failed` at the cap), the try is USED UP (not given back), and a late answer of the abandoned call is dropped by its helper thread and never written to the database.
  * A hung model therefore cannot freeze the reaper, which drives rows from its own thread (`test_reaper_survives_hung_model`, `test_hung_model_spends_the_try`, `test_late_answer_writes_nothing`). Not claimed: the model call itself is not stopped, an abandoned call runs on until it ends by itself.
  * At most `MODEL_HUNG_MAX` (4) model calls may run at once, healthy and abandoned ones together: the place is reserved under a lock BEFORE the helper thread starts, so the bound is exact (`test_workers_stay_within_the_cap`: 8 threads at once, at most 4 workers started).
  * With no place free, or when `Thread.start` raises `RuntimeError`, a drive that needs the model asks nothing: `ModelBusy`, the try is given back, `last_error` is `model_busy` and the row waits `MODEL_BUSY_BACKOFF_SECONDS` (5 s) before the next drive.
  * The give-back does NOT refresh `updated_at`, so such rows age into the stalled list of the review desk (`test_busy_give_back_keeps_the_age`, `test_busy_give_back_race_keeps_age`); when every place is held by an ABANDONED call the row is not even claimed (`_closed_kind`, `test_full_model_cap_shows_the_row`). `/counts` and the portal summary carry `hung_workers` (abandoned calls still running per kind: model, crm, send, refresh; additive, never changes `ok`), the desk logs one `error` line when a kind first has every place held by abandoned calls and one warning per burst of give-backs (`test_hung_workers_are_counted`, `test_full_cap_logs_once`, `test_thread_start_failure_is_busy`).
  * The model is therefore asked at most `SEND_MAX_ATTEMPTS` (5) times for one lead, because every timeout spends a try (`test_hung_tries_end_in_failed`); if four calls hang for ever the model path is closed until one ends or the desk is restarted, and the rows stay visible (in the stalled list).
  * The reaper takes a `sending` row only when it is strictly older than the stuck grace (send timeout + 5 busy waits, 30 s with the defaults; `updated_at < now - grace`, whole seconds; `test_reaper_needs_age_above_grace`).
  * The row is stamped before the model call and again right after the answer, and what must fit in the grace is the answer time plus the write of that second stamp. `MODEL_GRACE_MARGIN_SECONDS` (15 s) is the longest that one write can take: the write deadline (10 s) plus one more SQLite busy wait (5 s) for a lock held by another program.
  * The desk refuses to start if the budget plus the margin is not strictly below the smallest grace (25 s, the five busy waits alone; 9 + 15 = 24; an equal sum is refused, because the clocks count whole seconds) or if the margin is below the write deadline plus one busy wait (`test_margin_counts_the_busy_wait`); these checks run when `constants.py` and `desk.py` are imported, so a constant that is out of range ends with a Python traceback (the process ends with exit code 1), not with exit 4. A qualifier that declares a `timeout_seconds` that is not a number above 0 (zero, negative, NaN, infinity, a bool, a text, an integer too large for a float: `is_positive_seconds`) or above `MODEL_CALL_BUDGET_SECONDS` is refused when the `Desk` is built (`DeskSettingRefused`; exit 4 is also given by a `SettingRefused` from `Config.from_env` or from an adapter's `from_env`, see "Exit codes" below; `test_bad_declared_timeout_refused`, `test_declared_above_budget_is_refused`, `test_huge_number_is_a_refusal`).
  * The accepted limit is 9 s (9 accepted, 9.1 refused): a longer declared time would be cut off by the desk anyway. `timeout_seconds` is an honest wall-clock bound only if the adapter enforces a TOTAL deadline; the desk's own bound does not depend on it.
  * If the row is no longer ours when the model has answered (for example the desk clock was set forward and the reaper took the row), the label is not stored and the drive ends (`test_label_store_lost_claim_quiet`); the label write itself is guarded by `state='sending' AND attempts=<token>`, so a drive that lost its claim stores nothing (`test_label_store_needs_the_claim`).
  * A lock on the stamp or on the label write AFTER the model answered discards the answer and leaves the try USED UP (`internal:ModelAnswerLost`; a give-back would ask the model again without a bound, because a give-back does not count as a try), so the 5-try cap bounds the model calls (`test_locked_stamp_cannot_ask_for_ever`, `test_model_stamp_lock_spends_the_try`, `test_answer_lost_real_lock_keeps_try`; both writes, the stamp and the label write, are tested through the real retry loop); a lock on the first stamp, before the model is asked, still gives the try back.
  * If the row is later put back by the reaper, no send was started, so the portal card says nothing was sent (`ambiguous_prior` 0), not "the email may have left" (`test_answer_lost_card_not_email_left`); the "email may have left" wording stays for a row whose send may have started (`test_may_have_left_card_stays`).
* (5) A follow-up stuck in `sending` is put back by the reaper once it is older than send timeout + 5 busy waits (5 s + 5 x 5 s = 30 s with the defaults; strictly older, in whole seconds) without a restart; a restart does the same at once. The rule has exceptions, in this order.
  * (a) A row that never sent anything (the CRM step not finished, `crm_done` not 1, or no send mark, `send_started` 0) goes back to `pending` whatever the sender's mode, or to `failed` when it has already used its automatic tries (`SEND_MAX_ATTEMPTS`, 5; a person's Retry still starts it); it needs no capability read.
  * (b) Only a row whose send may have started follows the sender's mode: keyed -> `pending` (`failed` at the cap), blind -> `unknown`; while the sender's capability cannot be read such a row is left as it is.
  * A put-back does not give the automatic try back: a row for which no email was sent and the CRM was not written, because the row was put back five times in a row (the give-back write stayed locked each time, or a drive was held up past the grace; the AI step may have been asked), therefore ends `failed` with last_error `crash_while_sending`, and a person's Retry starts it again.
  * The desk cannot tell "the model was never asked" from "the model was asked and overtaken" (no column records it), and giving the try back would ask a hung model again without end; `test_unsent_row_at_cap_fails_visibly` pins this.

## Resolve check order (`POST /review/{item_id}/resolve`)
1. Body parse layer: `server.py` parses the JSON; `Desk.resolve(item_id, decision)` receives an already parsed `decision`. A body that is not JSON, or has no `decision`, or a `decision` that is not a string: 400 `{"error":"bad_decision"}` with NO item lookup (so even an unknown item id gives 400 here).
2. Item id grammar and existence: 404 `{"error":"not_found"}`. A malformed id such as `X1` is 404.
3. Item is an `R`, `D` or `O` item (except 3a): 409 `{"error":"not_actionable","hint":"..."}` (the decision value is not looked at).
3a.
* Approval mode only (`DESK_LATER_MODE=approval`), item is a `D` item: (a) the receipt is not a later message with new details (kind `replay_payload_differs`): 409 `not_actionable` as in step 3, decision not looked at; (b) `decision` does not fullmatch `approve:<approver id>` or `deny:<approver id>` (lower case, id `[a-z0-9][a-z0-9-]{0,31}`): 400 `bad_decision`; (c) the approver id is not in the approvers list: 403 `{"error":"not_an_approver"}`, nothing written; (d) ONE transaction `INSERT ... ON CONFLICT(receipt_id) DO NOTHING` into `later_decisions` and a read of the row; (e) this call wrote the row: 200 with the six keys `item_id, decision (approved or denied), decided_by, decided_by_name, channel (portal), decided_at`; otherwise 409 `already_decided` with the same six keys of the winner, also for the same person with the same word.
* Nothing else is touched: no lead, follow-up, CRM entry or email. With the mode `off` a `D` item is answered by step 3.
3b. Item is an `N` item (a reminder email; only when DESK_LEADFLOW_FILE is set): `decision` other than `seen`: 400 `bad_decision`; the reminder is `failed` or `unknown`: it is marked handled and the reply is 200 `{"item_id":"N...","state":"failed|unknown","handled":true}` (a repeat is 200 too); any other state (`pending`, `sending`, `sent`): 409 `{"error":"not_to_check","hint":"Only a reminder that is failed or unknown can be marked seen."}`. `seen` on an `F` item is 400 `bad_decision`. Nothing is ever sent by resolve.
4. `decision` not one of `sent`, `not_sent`, `crm_present`: 400 `{"error":"bad_decision"}`. (The server-side check of step 1 is a 400 before any lookup; this is step 4 inside Desk.)
5. Item is an `F` item whose state is not `unknown`: 409 `{"error":"not_unknown","hint":"..."}`.
6. Item is an `unknown` follow-up that this answer does not fit: 409 `{"error":"wrong_decision","hint":"..."}`. `sent` is accepted only when the CRM step is finished (`crm_done=1`: an email may have left); `crm_present` only when a CRM put was started and its end is unknown (`crm_done=2`: the person looked in the CRM and the row is there; it sets `crm_done=1` and the state `failed`, so Retry goes straight to the email); `not_sent` fits every `unknown` row and clears `ambiguous_prior`, and a leftover `crm_done=2` of a `crm_unconfirmed` row.

Retry (`POST /review/{item_id}/retry`) uses steps 2 and 3 in the same order (malformed id 404; `R`/`D`/`O`/`N` 409 `not_actionable`), then the retry-specific 409 codes. Retry on a `D` item stays 409 `not_actionable` in every mode: only resolve decides a `D` item (step 3a). `GET /review` is unchanged in approval mode (it lists the same items with the same fields).
Exact `hint` text for 409 `not_actionable` (same text for retry and resolve), by item type: `R` item: `Send a corrected submission with a NEW request number.`; `D` item: `Informational only, no action needed.`; `O` item: `Send the same request number again, or restart the desk.`; `N` item: `A reminder is never sent again by the desk. Check your mailbox, then mark it seen.`. 409 `not_unknown` (resolve) carries the hint `Only a follow-up in state unknown can be resolved.`. The retry codes `in_progress`, `unknown_needs_person` and `not_retryable` carry no `hint` (the table: `hint` only for `not_actionable` on retry).
`GET /counts?expected=` with an empty value (`expected=`), a non-integer or a negative number: 400 `{"error":"bad_expected"}`. No `expected` parameter at all: 200 with `expected_match` and `ok` as `null` where the table says so.

## Run commands
There is no build-system. Scripts set `PYTHONPATH=src` (and run from the repo root): `PYTHONPATH=src python -m lead_desk.server`, `PYTHONPATH=src:. python -m demo_only.fakes_server --outbox keyed --port 8766`, `PYTHONPATH=src:. python -m demo_only.burst ...`. (On Windows `;` separates the paths; the run scripts set it.) pytest sets the same paths itself (`pythonpath = ["src", "."]`) for its own process, but NOT for child processes: any test that starts a subprocess (`tests/crash_launcher.py`, the fakes server, `lead_desk.server`) passes `env["PYTHONPATH"]` (src and repo root joined with `os.pathsep`) to it. `schema.sql` is read with `importlib.resources` from the `lead_desk` package, so it is found relative to the package wherever `src` is on the path.

## Config environment names
`Config.fakes_url` is a read-only property built from `fakes_host` and `fakes_port`.
* Env names: `DESK_DB_PATH, DESK_BIND, DESK_PORT, DESK_ADAPTERS, DESK_FAKES_URL, DESK_FAKES_HOST, DESK_FAKES_PORT, DESK_REPLIES_PATH, DESK_SEND_TIMEOUT_SECONDS, DESK_SIZE_CAP_BYTES, DESK_STALL_SECONDS, DESK_ALLOWED_HOSTS, DESK_QUALIFIER` (`recorded` or `live_claude`), `DESK_OUTBOX` (`http`, `smtp` or `smtp_provider`), `DESK_CRM` (`fake` or `hubspot`).
* With `DESK_QUALIFIER=live_claude` the `DESK_LIVE_*` names are read (model, key file, prices and their date, run and total caps, ledger path, run id, base URL, API version, effort, timeout, max tokens; `docs/settings.md` lists them); with `DESK_OUTBOX=smtp` the `DESK_SMTP_*` names are read (host, port, from, message-id domain, timeout seconds); with `DESK_OUTBOX=smtp_provider` the `DESK_SMTPP_*` names are read (`HOST`, `PORT`, `SECURITY` = `starttls` or `ssl`, `USER`, `PASSWORD_FILE`, `FROM`, `RECIPIENTS` as a comma list, `MESSAGE_ID_DOMAIN`, `TIMEOUT_SECONDS`, `MAX_SENDS` (required hard cap), `STATS_FILE`, `CA_FILE`); with `DESK_CRM=hubspot` the `DESK_HUBSPOT_*` names are read (`KEY_FILE` and `MAX_CALLS` required, `BASE_URL`, `TIMEOUT_SECONDS`, `MAX_429_RETRIES`, `STATS_FILE`, `ALLOW_ANY_BASE_URL` = the word yes).
* A secret is never a value in these names: only the path of a one-line key file. `DESK_FAKES_URL` wins over `DESK_FAKES_HOST` / `DESK_FAKES_PORT`; its scheme must be `http` (anything else raises `ValueError`), a path other than empty or `/` raises `ValueError`, a query, fragment and userinfo are ignored (only host and port are taken); an IPv6 host keeps its brackets. `DESK_LATER_MODE` (`off` default, or `approval`) and `DESK_LEADFLOW_FILE` (a path to the lead flow file: the lead owner list, the lead stages and the reminder wait; unset, empty or the word `off` means the feature is off; exit 4 when the file is refused) and `DESK_NUDGE_TO` (the one address that gets reminders; refused unless the lead flow file is on) and `DESK_APPROVERS_FILE` (a path; refused unless the mode is `approval`; `config.approvers`, `config.approvers_label` are filled from the file by `server.main` through `loader.load_approvers`, exit 4 when refused; `Desk` refuses approval mode with no approver).

## Demo files
`demo_only/replies.json`: one JSON object, key = the normalised email key of a canned lead, value = `"hot"`, `"warm"` or `"cold"`.
* The canned leads file is `demo_only/canned_leads.json`: a JSON array of lead payloads (the payload shape of the HTTP table, made-up data), one per canned person. `test_demo_adapters` checks every canned lead email has a `replies.json` entry. `canned_leads.json` entries are payloads only: they carry NO `source` / `source_ref`; the scripts and tests that post them build the envelope with `source` = `form` or `webhook` (the envelope values of the HTTP table) and `source_ref` = `canned-<i>` where `<i>` is the position in the array (starting at 1). `RecordedQualifier` loading rules (fail loud): a missing `replies.json` or malformed JSON makes the constructor raise (never a silent empty mapping); a key with no entry answers `warm`; an entry whose value is not `hot`, `warm` or `cold` raises a `KeyError`-class error that names the bad label. `demo_only/fakes.py`, `fakes_server.py` and `burst.py` hold the fake CRM, the fake outbox, the recorded AI step, the fake servers and the burst script. `demo_only/approvers.json`: `{"label": "...", "approvers": [{"id","name"}, ...]}` (made-up approvers for approval mode; `label` optional), read through `loader.load_approvers` only (`DESK_APPROVERS_FILE` replaces it).

## Server and reply flush
The server writes the reply, calls `wfile.flush()` and `connection.shutdown(SHUT_WR)`, and only then runs `desk.run_followup`, so a client that reads until close is not kept waiting for the follow-up. `allow_reuse_address = (os.name != "nt")`; on Windows `SO_EXCLUSIVEADDRUSE` is set in `server_bind` under `if sys.platform == "win32":`. Windows limit (a restart on the same port is not tested by an automated test; tests use port 0): a restart on the same fixed port can fail for about 2 minutes (TIME_WAIT) and the conflicting bind can raise `PermissionError` instead of `EADDRINUSE`; the code catches `OSError` broadly, tests use port 0, and the launcher's 5 second bind retry may not outlast TIME_WAIT on Windows.

## Follow-up drive: who makes which claim
One private method `Desk._send_claimed(lead_id)` does the send and the recording of its result (send with `send_key=lead_id`, record the result) AFTER a won claim. The crash points `D1` and `D2` are inside it. Exactly two kinds of caller claim, and neither calls the other. Automatic drivers (`run_followup`, the reaper through `run_followup`, the start-up sweep, `handle`) claim only `('pending',)`; a person's `retry` claims `('pending','failed')` and starts the automatic count at 1:
* `run_followup(lead_id)` (also the start-up sweep for every `pending` follow-up, and `handle`): the claim first, `self._claim(None, lead_id, ("pending",))`; only if True, `_after_claim` runs steps 1-2 (the stage stamp, the AI label, the CRM row) and then `_send_claimed` (steps 4-5). The AI step is never asked before the claim.
* `retry(lead_id)` (HTTP Retry): its own `self._claim(None, lead_id)` whose UPDATE carries the state precondition `state IN ('pending','failed')`; if True, steps 1-2 then `self._send_claimed(lead_id)`; if False, it re-reads the state for the 409 code.
`_claim` always takes `None` today and opens its own transaction; a connection argument exists only for a caller that holds an open transaction-1 connection (`process` makes no claim). So `D1`/`D2` fire on first sends, Retry and the sweep, because all three reach `_send_claimed`.
* Writers of follow-up results (the first four below take the claim token, so a thread that lost its claim writes nothing): `_record_send_result` for `sent`, `pending`, `failed` and `unknown` in `sending` rows only (`WHERE state='sending'`); `_abort_unsent` for a claimed row whose step 1 or 2 failed (it goes through `_record_send_result`: back to `pending` with `internal:<class>`, `failed` only at the cap; the claim already counted the try; a lock or a lack of file handles goes through `_give_back` instead); `_mark_crm` and `_touch` for `crm_done` and the stamps of a `sending` row; `_requeue_sending` and `_pending_to_unknown` for the reaper and the start-up sweep.
* A row count of 0 is logged and ignored.

## Crash hook ownership
`lead_desk.hooks.FlagFileHooks(flag_path)` is the single shared hook for every subprocess crash.
* It reads a one-shot flag file (the path comes from config or the launcher, content = a point name), deletes it, prints "simulate crash" and calls `os._exit(137)`. `tests/crash_launcher.py` and `scripts/crash_desk.py` contain no hook code: each only calls `lead_desk.server.main(hooks=FlagFileHooks(path))`.
* The point names are `hooks.ALL_HOOK_POINTS`: `A`, `A2`, `B`, `D1`, `D2` (`HOOK_POINTS`) and `L` (the AI label is stored), `C0` (the CRM intent mark is written, the put not yet called), `C1` (the CRM put came back, `crm_done=1` not yet written), `D1b` (the send mark is written, `outbox.send` not yet called), `D3` (the result is recorded) and `N1` (a reminder email was sent, its result not yet recorded; only when the reminder is on) (`MORE_HOOK_POINTS`).
* In-process tests use their own `Hooks` subclass that raises `SimulatedCrash` (`test_crash_resume_each_point` for the first five, `test_crash_resume_after_*` in `tests/test_flow.py` for the other five, each with a keyed and a blind sender and a keyed and a blind CRM).
* A real process kill (`os._exit(137)`) is tested only at `D2`: `tests/test_http.py::test_crash_d2_subprocess` (fakes over HTTP, keyed and blind) and `test_crash_d2_subprocess_with_*` in `tests/test_http.py` (a real SMTP catcher).
* Hook A fires only when this call created the receipt row; hook B fires only when this call committed transaction 2 (a replay never fires either).

## Host and Origin gate
Every request, on every route, passes `_gate_error` in `server.py` before the path is read.
* (1) `Host` is required (sent once) and its name, port ignored and lower-cased, must be `127.0.0.1`, `localhost`, `[::1]`, the bind address (not when it is a wildcard address), or a name in `Config.allowed_hosts` (`DESK_ALLOWED_HOSTS`, comma list, each name a lower-case host name made of dot-separated labels of 1 to 63 letters, digits or hyphens that neither start nor end with a hyphen, at most 253 characters in all, or an IPv6 address in brackets; a wildcard address (four zeros, or `::`) is refused). A `Host` port above 65535 is refused too. Otherwise 403 `{"error":"forbidden_host"}`.
* (2) An `Origin` header, if present (sent once), must equal `http://<allowed name>:<bound port>` exactly; `null` and anything else give 403 `{"error":"forbidden_origin"}`.
* (3) A `Sec-Fetch-Site` header, if present, must be `same-origin` or `none`, else 403 `{"error":"forbidden_origin"}`.
  * A refused request writes nothing: no receipt, no count in `rejected_envelopes`; its body is read and dropped before the reply (the desk answers as HTTP/1.0 and never sends `100 Continue`; for a request with `Expect: 100-continue` the body is not waited for, so the refusal is immediate).
  * Requests without `Origin` and `Sec-Fetch-Site` (n8n's server side, scripts, tests) pass on `Host` alone. **The gate protects against browsers only** (cross-site pages and DNS rebinding). It is not authentication: anyone who can reach the bound address and types the right `Host` reads every lead.
  * Default bind is loopback; for a container bind the one bridge or host address, never a wildcard; the desk prints a warning at start-up when the bind is not loopback.
  * A caller that reaches the desk under another name (for example n8n in Docker, which uses the host name Docker gives the computer) sets `DESK_BIND` to the address the desk must listen on and `DESK_ALLOWED_HOSTS` to that name.

## Portal routes
Pages for a person (the pages only read; the buttons write: Retry and the “I checked” answers call `/review/...`; while the page sees the desk offline (any request that fails to reach the desk, on any page) or answering with a problem (a 5xx on the summary poll or the review poll; a 5xx on another page's own poll does not pause the buttons) those buttons are disabled with the line "Actions are paused until the desk answers." and nothing is sent to `/review/...`, the desk's own answers do not change; the Leads and Request log follow-up column shows the email state, and a row whose `state_view` is `crm_unconfirmed` shows "Waiting for the CRM check" plus the chip "CRM not confirmed", and the demo extension adds `POST /api/demo/crash` and `POST /api/demo/burst`): `GET /ui` answers 308 to `/ui/`; `GET /ui/<file>` serves one of the `.html`, `.css`, `.js` and `.png` files found under `src/lead_desk/portal/` when the server started (a fixed map, never a path read from the request; anything else is 404); `/ui/demo/<file>` serves a file of the demo extension when one is installed, else 404. `GET /api/ui/summary`, `/api/ui/leads`, `/api/ui/leads/<lead_id>`, `/api/ui/review` and `/api/ui/log` answer JSON built from ONE read transaction on a separate read-only connection (`mode=ro`, `PRAGMA query_only=ON`): a write through it fails. `GET /api/ui/data-map` opens no database (see its row below).
* All five that read the database, `/api/ui/review` included, read through that connection only (the review list runs `desk.review_rows`, the desk's own SQL and hint rules, on it); the desk's write connections are never used for a page.
* At most `PORTAL_MAX_INFLIGHT` (8) of these requests run at once; more get 503 `{"error":"busy"}`. `summary.refused_at_door` counts requests refused at the door since the desk started (in memory, 0 again after a restart); the Overview page shows it as "Requests turned away before they were stored" and it starts again at 0 after a restart. `GET /api/ui/leads?q=` matches (as plain text; case is ignored for ASCII letters only) the company and the lead id, and the name, the email address and the first request number only unless `by_email=0`, at most 100 characters, no control characters.
* Files are read once, when `portal_api` is first imported; symbolic links, files that resolve outside the portal folder and files over `STATIC_FILE_MAX_BYTES` are left out, and the folder name `demo/` is reserved for the extension: a file of the portal folder under that name is never served.
* Any other method on these routes is 405. `/api/demo/<rest>` goes to the demo extension (GET and POST only, any other method is 405; 404 when none is installed or when the desk does not run the demo adapters; a POST body must be `application/json`, else 400 `{"error":"bad_body"}`; a body over `DEMO_BODY_MAX` bytes is 413 `{"error":"too_large"}` and is not handed on; a body that stalls is 408 `{"error":"request_timeout","receipt_id":null}`).
* The extension is loaded before the socket is bound, so a broken extension leaves nothing listening.
* The failed-follow-up card (the desk's own title is "Follow-up failed") says "nothing was sent" only for the reasons `refused`, `unreachable` and `internal:*`; the reasons a person's own choice leaves (`person: not sent`: after the email question, "Follow-up failed; a person marked the email as not sent", Retry sends it now, with a reminder to check the mail system first; after the CRM question (the row's `crm_done` is 0 again), "Follow-up failed; a person marked the CRM entry as missing", Retry asks the CRM again and then sends the email; `person: crm row present`: "Follow-up not finished; the CRM entry is confirmed", Retry goes straight to the email) have their own words and never say the email may have left (the reminder to check the mail system is the only hedge); `crash_while_sending` with `ambiguous_prior` 0 (the row never reached the send) shows the card "The follow-up email was not sent" with "The desk stopped or was held up before it tried to send."; any other reason (`ambiguous`, others), and any failed follow-up whose row carries `ambiguous_prior` (an earlier send may have been sent), shows "Follow-up did not finish", because the email may have been sent, and Retry is safe only on a keyed outbox.
* Every reply, JSON or file, carries `Content-Security-Policy` (no inline script or style, no `data:`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy: same-origin` and `Cache-Control: no-store`.
* In approval mode the desk also decides a later message through `POST /review/D<n>/resolve` (the web address is open to any program that can reach the desk; there is no sign-in, the approver id is a name picked from the approvers list, not verified).

* Time stamps in table cells use the short form `34s ago`, `2m ago`, `3h ago`, `4d ago` (`just now` under 5 s); the tooltip has the full local and UTC time. At 1300 px and narrower the Leads table hides Source and Requests (the card never scrolls sideways and the page never does).

## Other rules
* `Config.replies_path` defaults to `None` ("the loader supplies its own default"): `load_demo_adapters` then uses the `replies.json` that sits next to the demo folder's package, found from the package file, not from the working directory. `DESK_REPLIES_PATH` still sets it. `loader.py` is the only product module that names the demo folder (a test enforces it).
* A submission with no email (a phone-only lead) has no lead key: verdict `review`, reason `incomplete:email` (or `incomplete:name,email` when the name is also missing); it is never merged and never dropped.
* A held lead-book lock raises `OSError` from `lockfile.acquire`. A `RecordedQualifier` label that is not `hot`, `warm` or `cold` raises a `KeyError` that names the label, from `qualify` (a follow-up then ends `failed` with `internal:KeyError`).
* Fakes server flag `--crm keyed|blind` (default `keyed`) selects the CRM's mode; `--outbox` is unchanged.
* `python -m lead_desk.server` prints one line `desk listening on http://<host>:<port>` when it accepts requests. The port in it is the real one, so `DESK_PORT=0` (ephemeral) works; the subprocess tests still pick a free port themselves.
  * Exit codes: 1 the sender cannot be reached, or a Python traceback (a constant that is out of range); 2 another desk holds the lock file; 3 the open-file limit is too low; 4 the desk refuses a setting, in any of three places: `Config.from_env` (a number that is not plain digits or is outside its range, any other bad `DESK_*` value), an adapter's `from_env` (a bad `DESK_SMTP*`, `DESK_HUBSPOT*` or `DESK_LIVE*` value), or when the `Desk` is built (an AI adapter whose `timeout_seconds` is not a number above 0 or is above the AI call budget of 9 s); the message names the setting; an error that is not a refused setting never gets code 4; 5 the port could not be bound within `BIND_RETRY_SECONDS` (any `OSError` is retried first, because on Windows a restart can meet the old port in TIME_WAIT). `EXIT_SIMULATED_KILL` 137 is only the crash scripts.
  * Refused connections (503 busy without a handler thread): after the reply the socket goes to one lingerer thread (`_Lingerer`, at most `LINGER_MAX_SOCKETS` = 16 at once, at most `DRAIN_TOTAL_SECONDS` each, ends at once when the client closes) which reads and drops request bytes still on their way, so the close does not send a reset (on Windows a reset destroys a reply the client has not read yet). A silent client costs the accept loop nothing. When the lingerer is full, bytes already there are read and the socket is closed. The 16 are counted in `FD_RESERVE_ITEMS`.
  * Start-up order:
* (1) the open-file check: exit 3 if `MAX_HANDLER_THREADS` needs more open files than this computer allows.
  * A handler thread is counted at `FDS_PER_HANDLER_THREAD` = 4 files: its connection socket, its database file, the `-wal` file of that database and the one adapter socket of the call it is making (a drive asks the AI step, the CRM and the sender one after the other, so it holds one adapter socket at a time).
  * The need is `FDS_PER_HANDLER_THREAD` x `MAX_HANDLER_THREADS` + `FD_RESERVE` (96).
  * The reserve covers, item by item (`FD_RESERVE_ITEMS`): the listening socket, the lock file, the standard streams and log handler, the one `-shm` file all connections share, the reaper's database connection, the portal's read-only database connections (8 at once, 2 files each) and the reaper's adapter socket; the desk refuses to start if those items add up to more than `FD_RESERVE`.
  * With the defaults the need is 4 x 1024 + 96 = 4192 open files: a computer whose hard limit is below that exits 3 (4096 is a common container default; raise it, for example `ulimit -n 8192` or the container's own setting, or the container's own open-file setting).
  * The 4 and the 96 are arithmetic, partly measured (`test_connection_holds_counted_files` for one connection, `test_reserve_covers_its_items` for the portal's connections; the other items are read from the code); DNS lookups and the temporary files SQLite makes are covered by the reserve only roughly.
  * The soft limit is raised to exactly the need, not to the hard limit, when the hard limit is unlimited or at least that. The refusal message names the open-file limit in force and what the desk needs.
* (2) The lock file (exit 2, "another desk is using this database").
* (3) The adapters (exit 1 if `/fake/info` cannot be read).
* (4) `Desk` is built (exit 4, `EXIT_DESK_SETTING_REFUSED`, if the desk refuses a setting here: an AI adapter that declares a `timeout_seconds` that is not a number above 0 or not below the stuck grace minus its margin; the message is printed and nothing is served; this code differs from exit 1 on purpose).
* (5) The bind (retried for `BIND_RETRY_SECONDS`, then exit 5).
* (6) The SIGTERM and SIGINT handler is installed, after the bind and before `desk.start_background()`, inside the `try` that holds the shutdown steps.
* (7) `desk.start_background()` (starts the reaper).
* (8) `Desk.startup()` (schema and sweep).
* (9) The listening line, then serve. When the accept loop gets no file handle (EMFILE or ENFILE) it pauses `ACCEPT_PAUSE_SECONDS` (0.05 s) instead of spinning.
  * Signals and shutdown: the first SIGTERM or SIGINT stops the desk like Ctrl+C: the serve loop ends, `desk.stop_background()` runs before the socket is closed (the reaper join waits up to 10 s), then the socket and the database connection are closed and the lock file is given back (a warning is logged if the reaper did not end in time). A second signal while these steps run is ignored on purpose, so it cannot cut a step short. What the operator does: wait about 10 s; if the process is still there, end it with SIGKILL (on Windows, end the process); the operating system drops the lock, and the next start puts every `sending` row back. A signal that arrives after the lock file is taken and before the handler is installed is not caught and ends the process at once.
* `Desk.run_followup` leaves a follow-up that is not `pending` alone (a second drive of a `sent` follow-up changes nothing). An exception in steps 1-2 after Retry's own claim goes through `_abort_unsent`: the claim started the automatic count at 1, so the row is `pending` with `internal:<class>` and a backoff (not `failed`), and the reply is 200 with `state` `pending` (a test runs it: `test_retry_step_error_is_pending`). A database that stayed locked gives the try back instead (except after the model answered: `ModelAnswerLost`, the try stays used up).
* Item existence for 404: `F<lead_id>` needs a follow-up row; `R<n>` a receipt with verdict `review`; `D<n>` a receipt with verdict `duplicate` and a non-empty `differing_fields`; `O<n>` an open receipt (any age). Anything else is 404.
* On `GET /review` the `reason` of a `duplicate_with_new_info` item is the JSON text of `differing_fields` (a string such as `["phone"]`), exactly what the view returns. The list is ordered by `since`, then `item_id`.
* Retry when the claim fails and the row is still `pending` or `failed` (the database stayed locked through the claim retries): 503 `{"error":"busy"}`.
* Lock-wait errors in the read and retry/resolve routes follow the same rule as `POST /leads`: busy gives 503 `{"error":"busy"}`, any other error 500 (except `/api/ui/*`, where the two "not ready" faults, "unable to open database file"/"no such table"/"disk I/O error", give 503 `{"error":"unavailable"}`) `{"error":"internal"}` (without `receipt_id` outside `POST /leads`).
* The server reads at most one byte more than `size_cap_bytes` of a body (enough to see that it is over the cap); after an early reply (a gate refusal or 413) it drops unread request bytes, up to `DRAIN_MAX_BYTES` or `DRAIN_TOTAL_SECONDS` of wall-clock time (1 s), whichever comes first, so the reply is not lost to a connection reset; a sender that is slower than that may still see the reply reset.
  * Draining, the header phase and the body phase each have a wall-clock limit (`DRAIN_TOTAL_SECONDS` 1 s, `HEADER_READ_DEADLINE_SECONDS` 10 s, `BODY_READ_DEADLINE_SECONDS` 10 s).
  * Writing a reply has one total wall-clock limit, `REPLY_WRITE_TIMEOUT_SECONDS` (5 s, never above `REQUEST_TIMEOUT_SECONDS`): a client that does not read its reply loses the handler thread after that time. Every other socket operation of a handler thread has a timeout of `REQUEST_TIMEOUT_SECONDS` (30 s).
  * Content-Length rules: a missing, non-numeric or conflicting (two different values) header is 400 `bad_envelope`; a value over the cap is answered 413 at once, before any body byte is read, whatever its length (a 4301-digit number included; more than 18 significant digits is treated as over every limit); the same cap holds for the body of `POST /review/<id>/resolve` (the Host and Origin check still comes first): over the cap is 413 `{"error":"too_large"}` (no `receipt_id`, not counted in `rejected_envelopes`), exactly the cap is read; a missing or conflicting Content-Length there stays 400 `bad_decision`; a body shorter than announced is 408 `request_timeout` once `BODY_READ_DEADLINE_SECONDS` (10 s after the end of the headers) has passed, if the connection stays open, or 400 `bad_envelope` if the sender closes it.
  * Rows 400, 408 and 413 on `POST /leads` count in `rejected_envelopes`. A request target the standard library cannot split (for example `http://[/`) is 400 `{"error":"bad_request"}`. A review item id whose number has more than 18 digits is 404 `not_found` (no item can have one).
  * The follow-up id of a new lead is taken before the reply is written and the follow-up runs in a `finally`: if the reply cannot be written (the sender reset the connection) the follow-up still runs. The listen backlog is `LISTEN_QUEUE` (1024); the operating system may cap it lower.
  * Connection limit: at most `MAX_CONNECTIONS` (256; accepted range 8 to 4096, checked when `constants.py` is imported) connections are in their read phase at once; a connection's place ends when the desk starts writing its reply.
  * Request line plus headers have `HEADER_READ_DEADLINE_SECONDS` and the body `BODY_READ_DEADLINE_SECONDS` (wall-clock); a stall in any of them (header, body, resolve body, demo body) is 408 `{"error":"request_timeout","receipt_id":null}`.
  * At the cap the oldest connection that is still being read (request line, headers or body) AND has received no byte for `EVICT_MIN_IDLE_SECONDS` (2 s; accepted range above 0 and not above either read deadline, checked when `constants.py` is imported) is closed with no reply; its sender sees a dropped connection and nothing was stored.
  * A connection that is still sending is never the one closed. A connection stops being closable at `start_work`, which is after its whole request has been read, the JSON parsed and the envelope checked and just before the desk acts on it (so a request that has a receipt is never closed), and while it replies or drains.
  * If no connection can be closed, the new connection gets a full 503 `{"error":"busy","reason":"busy"}` with `Retry-After: 1`, `Content-Length`, `Connection: close` and the security headers.
  * This body is its own form: the `reason` key is there on purpose, so a client can tell this refusal (nothing was stored, no receipt exists) from the 503 `{"error":"busy"}` of a database lock or of the portal.
  * The reply is written within `BUSY_WRITE_TIMEOUT_SECONDS`, and the desk then reads and drops only the request bytes that have already arrived (it never waits for more, so a silent client costs the accept loop no time), for at most `QUIET_DRAIN_SECONDS` (0.05 s) in total, so a refused client that keeps sending cannot hold up the next connection.
  * Bytes that arrive after that can still cause a reset of that refused connection. Second limit: at most `MAX_HANDLER_THREADS` (1024; accepted range 8 to 65536 and not below `MAX_CONNECTIONS`, checked when `constants.py` is imported) handler threads exist at once.
  * A thread counts from the moment the server hands it a connection until it ends, so the reply write, the draining and the follow-up after the reply count too (the 256 limit counts only the reading part). At that limit the new connection gets the same complete 503 busy and nothing is stored.
  * At start-up the open-file limit must cover 4 files per handler thread (`FDS_PER_HANDLER_THREAD`) plus `FD_RESERVE` (96); see the start-up order above.
  * If the follow-up cannot open a connection because the desk is out of file handles (`EMFILE`/`ENFILE`), nothing was sent: the row goes back to `pending` with `last_error` `no_descriptors` and no automatic try is used up; such a row waits `NO_DESCRIPTORS_BACKOFF_SECONDS` (5 s) before the next drive, so the reaper does not drive it again on every pass while the shortage lasts.
  * The same holds when the file-handle shortage hits the read of the sender's mode before a send that is flagged `ambiguous_prior`, or the read of the CRM's mode before a leftover `crm_done=2` is judged: nothing was asked, so the try is given back (an unreadable mode for another reason still counts as an unreachable sender, or ends `unknown` for a CRM that is not keyed).
* Adapter timeouts: on Windows a refused connect to a closed local port reports only after about 2 seconds. A shorter send timeout turns "refused" into a connect timeout, which the table classes as ambiguous. The default `send_timeout_seconds` is 5.0, so the default is unaffected.

## Follow-up handling reference
These rules are part of this contract. Where one differs from a table row above, the table row is wrong and is fixed.

### Replies, verdicts and review items
- POST /leads: a `source_ref` with a control character (NUL included), outside 1..128 characters, or holding a lone surrogate, and an unknown `source` (when it reaches `Desk.process`), give 400 `{"error":"bad_envelope","receipt_id":null}`, no receipt, counted in `rejected_envelopes`. `server.py` checks the length and `Desk.process` repeats the check and adds the control-character rule.
- Verdict `review`, reason `bad_field:<field>`, for any control character (Unicode category Cc, NUL included) in name, email, phone or company, and in message except tab, line feed and carriage return. Also for name, phone and company: any format character (category Cf: zero-width space and joiner, byte-order mark, right-to-left override) and the line and paragraph separators (Zl, Zp: U+2028, U+2029). Message: Zl, Zp and the direction controls (U+202A to U+202E, U+2066 to U+2069); the zero-width joiners that emoji need are allowed in a message.
- Reason `internal_unstorable`: a payload that passed every check but was still refused by the database (an integrity, value or overflow error that is not a lock) gets verdict `review` and an open receipt, not a 500. Also RecursionError, `sqlite3.DataError`, a stored payload that is not readable JSON and a lone surrogate (UnicodeError). A plain ValueError is not caught: it is a 500 `internal` and the receipt stays open (the reaper and a restart try again). A payload nested so deeply that it cannot be written down in `Desk.process` is 400 `bad_envelope` (counted in `rejected_envelopes`), as at the HTTP layer.
- Reason `internal_error`: a receipt that cannot be decided because of a plain error that is not a lock and not an "unstorable" error gets verdict `review` after 3 failed tries in a row (`gate.DECIDE_FAIL_LIMIT`; counted per receipt in memory, a restart counts again from 0). A database that stays locked is never counted.
  * A database fault that is not a lock (`sqlite3.OperationalError`: disk I/O error, disk full, a file held by another program, no file handle left) is transient: it never counts towards the 3 tries and never writes a verdict.
  * The receipt stays open, is added to the desk's poke list so the reaper tries it again at every pass (it does not wait for `stall_seconds`), shows as stalled in the review list, and is counted in `/counts` as `decide_transient_errors` (in memory, 0 after a restart); the request itself gets an error reply (500), so a sender that repeats the SAME request number is correct and safe.
  * A broken database constraint (`sqlite3.IntegrityError`) is not transient: the receipt gets verdict `review` with reason `internal_unstorable:integrity` (plain `internal_unstorable` for an unstorable value such as a surrogate), and `/counts` counts it in `decide_integrity_errors` (in memory); while that counter is above 0, `/counts` `ok` is false.
  * The review hint for `internal_error` says the same fault came up again and again, a person must look at the desk log and fix the cause, and the lead can then be sent again with a new request number.
- Email: an apostrophe is allowed before the @ (o'brien@example.com); every other exclusion stands. A character that lower-cases to ASCII (the Kelvin sign U+212A gives k; U+0130 gives i plus a mark) is refused: verdict `review`, reason `invalid_email`. Other non-ASCII letters are accepted (the key is their lower-case form). The desk does not normalise to NFC: two spellings of one mailbox stay two leads, which can split a mailbox but never merge two.
- POST /leads: 503 `{"error":"busy","receipt_id":null}` is also answered when 32 requests are already inside the desk and no place frees up within 5 s. No receipt is written then, so the client can send the same request again. A 503 `busy` that comes after the receipt was written leaves the receipt open; the reaper decides it at its next pass (it does not wait for `stall_seconds`) and the client may send the same request number again (a replay of the open receipt). "No open receipt after a 503" holds only for a 503 that comes before the receipt was written.
- Follow-up send results: a reply that came back with the wrong mode is `unknown` / `mode_mismatch`.
  * A refused or unreachable sender (nothing sent), an unclear end on a KEYED sender (sending again is safe), a CRM that failed, or an AI step that failed puts the follow-up back to `pending` (last_error `refused` / `unreachable` / `ambiguous` / `internal:<class>`). `attempts` counts the claims (the starts of a try) and is never lowered, because it is the ownership token; the automatic tries that set the cap are counted in `auto_attempts`, which a give-back lowers.
  * The reaper tries again after 1, 2, 4, 8 s; after 5 automatic tries in all (`SEND_MAX_ATTEMPTS`) the row is `failed`. Only an unclear end on a BLIND sender goes to `unknown` at once (the email may have left; a person decides).
  * A person's Retry starts the count again (try 1): if the sender refuses once more the follow-up is `pending` again (backoff running), not `failed`.
- The AI step's answer must be one of hot, warm, cold (checked in `_label_step`). Anything else is an error of the AI step (`internal:ValueError`, one automatic try); the CRM is not asked and the label stays empty.
- POST /review/{id}/retry never answers 200 with state `sending`; if the result could not be recorded it answers 409 `{"error":"in_progress"}`.
- GET /counts: `received = new + duplicate + review + open` (`test_reconcile_counts`). A refused request (bad envelope, too large) has no receipt, so it is not in `received`; it is counted apart in `rejected_envelopes`, an in-memory counter that starts at 0 after a restart.
  * There is no failed receipt outcome. `failed_followups`, `unknown_followups`, `sending_followups` are integers. `pending_followups` means pending + sending. `ok` is true only when open = 0, rejected_envelopes = 0, `decide_integrity_errors` = 0, expected matches, pending_followups = 0, failed_followups = 0 and unknown_followups = 0. So a refused body (400, 408 or 413 on `POST /leads`, which all count in `rejected_envelopes`) makes `ok` false until the desk restarts; a 403 from the Host and Origin gate does not count. `rejected_envelopes` is an in-memory counter of this process (it resets at restart). `reaper_running` is true while a reaper thread is alive and `last_reaper_pass_at` is the epoch second at which the last reaper pass ended (`null` before the first).
  * Both are information only: they never change `ok`. The reaper loop catches every exception from a pass (including ones that are not `Exception`) and goes on with the next pass; a reaper that is not running shows as `reaper_running: false` on a desk that was started with one.
- Review list: a request number that comes again with a different payload keeps its first answer (`payload_matches:false`) and adds a D item `D<receipt_id>`, kind `replay_payload_differs`, reason `same request number, different payload`, informational (retry and resolve answer 409 `not_actionable`). If the receipt is also a duplicate with new information there is still ONE D item (kind `duplicate_with_new_info`). In approval mode (`DESK_LATER_MODE=approval`) a `duplicate_with_new_info` item is decided through resolve (check order step 3a); retry still answers 409 `not_actionable`, and a `replay_payload_differs` item can never be decided.
- Review item and retry/resolve ids: a number with a leading zero (R0012) or more than 18 characters is 404 `not_found` (an item has exactly one id).
- `Desk.process` never raises for non-JSON-native direct input (mixed-type keys, a set, a date, a 4301-digit number): 400 `bad_envelope`, counted in `rejected_envelopes`. `Desk.review`, `lead` and `counts` answer through the error shell (500 `internal` or 503 `busy` as bodies) instead of raising; `lead` of an id with a control character or lone surrogate is 404.
- Adapters: a reply is read up to `constants.REPLY_MAX_BYTES` (1 MiB; longer is an error, treated as unclear like any bad reply); a 3xx answer is an error and is never followed.

### Schema and migration
- Rules of the desk's records in `schema.sql` (proved by `test_write_once_triggers`): `receipts` cannot be changed or deleted and a verdict is written once; `leads` cannot be changed or deleted; `followups` cannot be deleted (trigger `followups_no_delete`, which also stops `INSERT OR REPLACE`) and a `sent` row is final; `receipts` has `CHECK (outcome IS NULL OR outcome <> 'new' OR outcome_lead_id IS NOT NULL)`.
  * The CHECK exists only in a freshly created book (SQLite cannot add it afterwards). `db._migrate` runs `schema.sql` again, which creates any missing trigger, when the book is missing a column, the view, an index or a trigger; a book without a trigger is repaired and then refuses deletes (`tests/test_migration_triggers.py`). `later_decisions` (approval mode) cannot be changed or deleted (triggers `later_decisions_no_update` and `later_decisions_no_delete`, the second also stops `INSERT OR REPLACE`): one row per later message, the first writer wins.
- `PRAGMA user_version` is 1. Columns: `receipts.payload_conflict`, `followups.crm_done`, `followups.auto_attempts`, `followups.ambiguous_prior`, `followups.send_started`.
  * The view `review_items` and the indexes (two partial ones, `receipts_open_ix` on open receipts and `followups_active_ix` on pending and sending follow-ups, plus `receipts_time_ix` and the unique `leads_email_key_uq`) belong to the schema.
  * A desk's records made by an older version of the desk gets the columns, their backfills, the view and the indexes in ONE transaction at start-up (`db._migrate`): a crash in the middle changes nothing, and a book that has the columns but lost the view or an index is repaired at the next start.
  * Backfills for books migrated this way are not corrected afterwards. The table `later_decisions` (approval mode, see Resolve check order step 3a) is created by the same script and is part of the schema; its two triggers are in the repair list.
- `crm_done` backfill: a `sending` row gets 2 (a put may have started; the safe path decides); a row whose `last_error` starts with `internal:` (the CRM or AI step broke) keeps 0, so the next try asks the CRM; a `failed` row with a label and any other error gets 1 (older books asked the CRM before the first send); any other row that was tried (`pending` or `unknown`, attempts > 0) gets 2. A `sent` row is never touched.
- `ambiguous_prior` backfill: 1 for a `pending` row whose last_error is `crash_while_sending`. `send_started` backfill: 1 for a `sending` row with `crm_done=1` (it may have sent: the safe side), 0 elsewhere.
- Journal mode: `db.connect` raises RuntimeError unless the file is in WAL mode (a private `:memory:` book is exempt).
- Lock file: the db path is resolved first (symlinks). BlockingIOError means another desk. On Windows only EACCES (locking violation) and EDEADLK mean another desk. Any other OSError, and a lock file that keeps being replaced (3 tries), give `LockUnavailableError` (the lock could not be taken for another reason; still a refusal).
- The lead-book path is resolved once in `Desk.__init__` (`Desk._db_path`) and used for the connections and the write gate, so a later chdir cannot send a new thread to another file.

### Ownership of a follow-up and the CRM mark
- Claims: `Desk._claim(conn, lead_id, from_states)`. `run_followup`, the reaper and the start-up sweep claim only `('pending',)`; only a person's Retry claims `('pending','failed')` (and starts the automatic count at 1). Any other state list raises ValueError. A claim that failed with an exception clears the thread's ownership token.
- Ownership: the claim's `attempts` value is the owner's token. Every write of the drive that won the claim (`crm_done` marks, the stage time `updated_at`, the send result) only matches `state='sending'` AND the same `attempts`. A drive that stalled and was put back by the reaper therefore changes nothing in a later drive's claim (no second CRM put, no overwritten result). `updated_at` is moved right after the claim, before the AI step. `_mark_crm`, `_touch`, `_record_send_result`, `_crm_step` and `_send_claimed` take the token; `_claim` returns a bool.
- Stage times: `updated_at` of a `sending` row is moved to now before the CRM put (the intent mark) and before the send, so the reaper's grace (send timeout 5 s + 5 busy waits of 5 s = 30 s; a row is taken only when strictly older) counts from the last stage. If the row is no longer `sending` at that moment (the reaper took it back), the stage is not run. `_touch` answers "not ours" (False) only when the row really is not ours (token or state changed; nothing is written, the drive stops without changing anything). A lock that stays held raises the busy error instead, and the drive gives its try back; before the send this means: no mark, no send.
- CRM: the CRM put runs only after a won claim. `followups.crm_done` is an intent mark: 0 not asked, 2 a put was started (written BEFORE the put, together with a fresh `updated_at`), 1 the put came back. `crm_done=1` is written in a retried transaction; if it still cannot be written the drive does NOT go on to the send: the row stays `sending` and the reaper puts it back flagged `ambiguous_prior` (the leftover 2 then follows the keyed / not-keyed rule below).
- A leftover 2 (the desk died, or the write of 1 failed) means the put may have reached the CRM. A CRM that is keyed (a `capability` attribute equal to `keyed`) is simply asked again (harmless).
  * Any other CRM, and a CRM with no `capability` attribute (the in-process demo `FakeCrm` has none), is not asked again: the follow-up becomes `unknown`, last_error `crm_unconfirmed`, and a person looks in the CRM. The same happens at once when a put of such a CRM ends unclear (timeout, reset, 5xx, odd answer).
  * A put that provably stored nothing (the exception has `nothing_stored` true: refused with a 4xx answer, or not reached; `HttpCrm` also raises `CrmNothingStored` when no file handle was left for the connection, EMFILE or ENFILE) resets the mark to 0 and the follow-up is tried again after the backoff, on a CRM that is not keyed too.
  * For a keyed CRM there is no window for a second record; for a CRM that is not keyed no second put is ever made without a person's decision.
- When the desk cannot read the CRM's mode at all for a leftover 2 (the CRM is down; nothing is asked in that try) it does not judge: the try is used up with a backoff (`internal:CrmUnreachable`; the failed card tells a person that the CRM row may already exist), the mark stays 2, and the cap ends the row `failed`, which a person's Retry starts again; the next readable mode then decides. If the read failed only because no file handle was left (EMFILE or ENFILE), nothing can be judged: the try is given back (row `pending`, mark stays 2, `last_error` `no_descriptors`).
- `HttpCrm.refresh()` reads `crm_capability` from GET /fake/info (the shipped fakes server answers it); the desk calls it at start-up, whenever it reads the sender's mode again, and before it judges a leftover `crm_done=2`.
  * When the read cannot be made (the server is down, the answer is not JSON, the key is missing) the adapter forgets its value (`None`, which counts as not keyed: the safe side) and raises `CrmError`; an answer that names no mode (anything but `keyed` or `blind`) raises `CrmError` and keeps the last good value.
  * A refresh that finds the adapter busy counts as a failed read, so a keyed CRM is judged not keyed while the four refresh places are held by calls that never returned (the safe direction).
  * The answer of an abandoned read never overwrites the result of a read that started later (`test_late_refresh_keeps_newer_mode`; the same rule is coded for a put, but no test proves it). `HttpOutbox` keeps capability and mode as ONE tuple (a reader never sees half a change). `test_shipped_fake_answers_crm_mode` runs `HttpCrm.refresh()` against the shipped fake.
- `ambiguous_prior` is set when an email may have left (a start-up or reaper requeue of a `sending` row with `crm_done=1` and `send_started=1`, an unclear end of a keyed send). A row with it is never sent by a BLIND sender: it becomes `unknown`, last_error `ambiguous_prior` (the reaper does this without a claim, `_send_claimed` does it as the last check before sending, and `_pending_to_unknown` sets the same `last_error`). Before such a row is sent the sender's mode is read again (`_refresh_outbox`); if it is blind now the row becomes `unknown`; if it cannot be read, nothing is sent and the row goes back to `pending` (`unreachable`, one automatic try).
- `send_started` is the intent mark of the send: every claim clears it, and the same UPDATE that moves `updated_at` just before `outbox.send` sets it. A `sending` row with `send_started=0`, or with `crm_done` not 1, never sent anything: a requeue (start-up or reaper) puts it back to `pending` (`failed` at the cap) on a blind sender too, and the CRM rule decides at the next drive. If the mark cannot be written (a lock), nothing is sent. With the sender's mode unread, only rows that may have sent wait for the read.
- A `sending` row put back with `auto_attempts` already at the cap goes to `failed` (keyed sender; a person's Retry still works) instead of `pending`; a blind sender gives `unknown` for a row whose send may have started.
- POST /review/{id}/resolve, `crm_present`: accepted only for an `unknown` follow-up with `crm_done=2` (a CRM put was started and its end is not known), whatever its `last_error`.
  * It sets `crm_done=1` and the state `failed` (last_error `person: crm row present`), so the person's Retry goes straight to the email without asking the CRM. `sent` is accepted only for an `unknown` row with `crm_done=1` (an email attempt followed); for any other `unknown` row `sent` and `crm_present` are 409 `wrong_decision` with a `hint`. `not_sent` fits every `unknown` row, clears `ambiguous_prior`, and clears a leftover `crm_done=2` when the row is `crm_unconfirmed`, so the next try asks the CRM again (check the CRM first: an extra row may need deleting by hand). `not_sent` is refused with 409 `call_still_running` while a send or CRM call of that lead that the desk gave up on is still running. `bad_decision` (400) means "not one of sent, not_sent, crm_present".
- Hints: a 409 `wrong_decision` and a review item of kind `unknown` carry a `hint` (a plain sentence). For a `crm_unconfirmed` item: "The CRM may or may not hold this lead. Look in the CRM, then answer crm_present (the row is there) or not_sent (the row is not there). sent is refused: no email was tried." For an unknown row whose CRM step is finished: "The CRM row is already done; what is unclear is the email ... crm_present is refused here."
- A failure before the send (reading the row, the mode read, the intent mark) is not taken for an unclear send: it counts as one automatic try (`internal:<class>`, row `pending`). Only `outbox.send` itself decides `ambiguous`, and a send that the desk stopped waiting for (`SendAmbiguous` from the total deadline) counts as ambiguous too.
- A lock inside the steps after the claim (the first stage stamp, the AI step, the stamp after the AI step, the CRM mark, the stamp that writes the send mark) is not an error of the follow-up: the claimed try is given back (`auto_attempts` minus 1, row `pending`, `send_started` 0, no `last_error`), only if this claim's token still matches. The one exception is a lock on the stamp or label write after the model answered (`ModelAnswerLost`): the try stays used up. The give-back write is retried like any other write (`_locked_retry`). If even that stays locked, the row stays `sending` and the reaper puts it back (a row whose send mark was written then counts as a send that may have started: `unknown` on a blind sender, the safe side).
- A client replay of a `new` request drives the follow-up only if it is due: no automatic try yet, or its backoff is over. Replays cannot use up the 5 tries.
- A `pending` or `sending` row stamped later than now (the clock was set back) is set to now by the reaper, then ages normally. An open receipt stamped in the future counts its age from the first reaper pass that saw it open.

### Reaper, gates and load
- Start-up: `Desk.startup()` raises RuntimeError when called twice, after the desk served or drove anything, or after a `retry`, `resolve` or `_claim` call. With `start_background()` called first, start-up does not drive pending follow-ups (the reaper does), so serving starts at once.
- The reaper reads the sender's capability again only when a `sending` row is stuck, after a wrong-mode reply, or at most every 30 s (`gate.OUTBOX_REFRESH_SECONDS`); no requeue decision is made when the capability could not be read (start-up leaves such rows `sending` for the reaper).
- A reaper pass drives rows for at most `gate.REAPER_PASS_SECONDS` (10 real seconds); the rest is still due and comes first in the next pass.
- Write gate: one per resolved lead-book path (`gate.gate_for`), so desks on different books do not wait for each other. It is not re-entrant: nothing may ask for it while holding it (`Desk._write` is never nested). It has two lines: request writes first, drive and reaper writes second (`FairGate.acquire(timeout, low)`). A wait for the gate that runs out is NOT tried again (no new ticket at the tail). All tries of one write share one deadline (`gate.WRITE_DEADLINE_SECONDS` = 10 s); a whole `process` call has one deadline (`gate.REQUEST_DEADLINE_SECONDS` = 15 s) that includes the in-flight wait.
- In-flight limit: a first-come-first-served counting semaphore (`gate.FairSemaphore`, 32 places). Follow-up drives have their own 8 places (`gate.DRIVE_MAX`); a drive that finds no place within 5 s is left to the reaper (only when `start_background()` was called; without a reaper it waits for its place, because nobody else would drive the row).
- The reaper's stuck grace is send timeout + 5 busy waits (30 s with the defaults), longer than the longest result write (write deadline 10 s + one SQLite busy wait 5 s) and than the model bound plus the stamp that follows it (9 s + 15 s).

### Known limits of the desk
- The reaper drives rows one after another, not in parallel. Schema writes bypass the write gate: they happen only at start-up, before serving. A crash hook that asks for the gate again would deadlock for one wait: hooks are test seams.
- Start-up counts a try for a row whose backoff has not passed. The adapter's own timeout is per socket operation, not total; the desk therefore bounds the CRM put, the send and the capability reads with a TOTAL deadline of its own (`Desk._bounded`, see `docs/limits.md`).
- A duplicate reply returns the id of the other lead: kept as it is.
